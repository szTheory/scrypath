### New release_parity step (D-18)

Positioned AFTER the existing `verify.release_publish` step (currently at ~L75-80). Copies the existing `if:` guard and `env:` block to inherit the same behavior.

```yaml
      - name: Verify release-parity against latest published version
        if: ${{ steps.resolve-version.outputs.published == 'true' }}
        env:
          SCRYPATH_RELEASE_VERIFY_ATTEMPTS: "10"
          SCRYPATH_RELEASE_VERIFY_SLEEP_MS: "15000"
        run: mix verify.release_parity "${{ steps.resolve-version.outputs.version }}"
```

### New drift-issue step (D-19)

Positioned AFTER the release_parity step. Guarded on `failure() && github.event_name == 'schedule' && steps.resolve-version.outputs.published == 'true'`. Uses `JasonEtco/create-an-issue@v2` with `update_existing: true` for per-version dedup.

```yaml
      - name: Open drift issue (scheduled runs only)
        if: ${{ failure() && github.event_name == 'schedule' && steps.resolve-version.outputs.published == 'true' }}
        uses: JasonEtco/create-an-issue@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          VERSION: ${{ steps.resolve-version.outputs.version }}
        with:
          update_existing: true
          search_existing: open
          filename: .github/ISSUE_TEMPLATE/release-parity-drift.md
```

### Permissions block (Security V4)

Current workflow top-level permissions includes `contents: read`. Add `issues: write`:

```yaml
permissions:
  contents: read
  issues: write
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub cron scheduler → workflow run | GitHub-controlled trigger; no user input beyond cron expression |
| `mix verify.release_parity` subprocess → public Hex + public git | Both sides are public read-only reads |
| `create-an-issue@v2` → GitHub issues API | Uses `${{ secrets.GITHUB_TOKEN }}` with scope limited by workflow `permissions:` block |
| Issue template mustache interpolation → issue body | Env vars flow from workflow step to template body; no user input path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-18-06-01 | I (Info Disclosure) | GitHub token logging | mitigate | `create-an-issue@v2` reads `GITHUB_TOKEN` from env silently; the workflow never `echo`es it. Standard GitHub Actions log masking also redacts it. |
| T-18-06-02 | E (Elevation of Privilege) | Over-broad workflow permissions | mitigate | `permissions:` block scoped to `contents: read` + `issues: write` only. No `pull-requests`, `packages`, `deployments`, etc. Follows principle of least privilege. |
| T-18-06-03 | I (Info Disclosure) | Drift issue leaks private info | mitigate | Issue template body contains ONLY public data: version string, public workflow run URL, and the pointer to the already-public .planning/milestones/v1.2-MILESTONE-AUDIT.md. No file contents, no secrets, no internal paths. |
| T-18-06-04 | D (DoS) | Scheduled run file-storm on prolonged drift | mitigate | `update_existing: true` + `search_existing: open` ensure a single open issue per version. Title includes `{{ env.VERSION }}` so v0.4.0 drift vs v0.5.0 drift get distinct issues, but repeated scheduled runs of the same version collapse into one issue. |
| T-18-06-05 | R (Repudiation) | Silent workflow change (e.g. attacker adds `continue-on-error: true` to hide drift) | mitigate | Acceptance criteria grep explicitly forbids `continue-on-error: true` on the release_parity step. `workflow_wiring_test.exs` (INFRA-02/04 describes) asserts presence of guard, action ref, and dedup flag — removing any breaks the suite. |
| T-18-06-06 | T (Tampering) | `JasonEtco/create-an-issue@v2` supply-chain | accept | Pinned to major tag `@v2`; a maintainer-owned community action. Could be pinned by SHA for defense-in-depth (backlog) but not in Phase 18 scope per D-19 wording. |
| T-18-06-07 | S (Spoofing) | Actor impersonating scheduled runs to file issues | mitigate | `github.event_name == 'schedule'` is set by GitHub's scheduler, not the workflow YAML — cannot be forged by a workflow_dispatch run. |
</threat_model>
