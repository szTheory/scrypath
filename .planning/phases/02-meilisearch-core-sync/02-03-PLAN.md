## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| accepted task metadata -> caller-visible results | Meilisearch task responses influence whether inline sync returns success or failure. |
| polling loop -> caller latency | Inline mode consumes wall-clock time while waiting for terminal backend state. |
| backend failures -> application error handling | Failure classification must be preserved so callers can react appropriately. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 | Tampering | task status normalization | high | mitigate | Normalize accepted tasks in one module and cover success, failure, cancellation, and timeout behavior in tests so `202 Accepted` can never be misreported as terminal success. |
| T-02-08 | Denial of Service | inline polling loop | medium | mitigate | Drive polling with validated timeout/interval config and require timeout tests so inline mode cannot hang indefinitely. |
| T-02-09 | Repudiation | returned failure classes | medium | mitigate | Preserve distinct error tuples for transport failure, timeout, backend task failure, and cancellation so caller-visible behavior remains auditable. |
</threat_model>
