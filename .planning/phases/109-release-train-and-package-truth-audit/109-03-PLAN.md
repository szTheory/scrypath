## Trust Boundaries

| maintainer docs -> workflow implementation | Stale docs can instruct maintainers to use a different authority than the actual workflow chain. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-109-01 | Tampering | `release-please.yml` / `publish-hex.yml` version propagation | mitigate | Assert exact tag/version propagation and ordered proof steps in `workflow_wiring_test.exs`, then patch YAML drift directly. |
| T-109-02 | Tampering | published package truth and live monitor boundaries | mitigate | Keep publish-free monitor behavior in `verify-published-release.yml` and leave artifact/package proof to Plan `109-01`. |
| T-109-03 | Tampering | workflow/docs drift removing critical proof checks | mitigate | Align workflow tests, `docs/releasing.md`, and `CONTRIBUTING.md` to the same canonical chain and recovery semantics. |
| T-109-04 | Elevation | workflow version input to live verification | mitigate | Keep `inputs.release_version` and workflow output usage explicit, constrained to existing verification commands, and covered by ordered tests rather than ad-hoc shell plumbing. |
| T-109-SC | Tampering | npm/pip/cargo installs | accept | No new package-manager installs or action additions are introduced in this plan. |
</threat_model>
