# Phase 177 UI Baseline Audit

## Scope and evidence identity

This is the Plan 177-01 baseline for the six current ScrypathOps surfaces. The inspected implementation source is commit `cc53498abcd6d8862e9c23f155b4028ee16dbd44`; the direct matrix test was committed before capture, and no runtime UI source changed afterward. `DESIGN.md` and `DESIGN-TOKENS.md` were reconciled after the captures against that same implementation.

The root guide follows the eight-section body order in the [official DESIGN.md format spec](https://raw.githubusercontent.com/google-labs-code/design.md/main/docs/spec.md). It omits optional YAML frontmatter because `app.css` and `DESIGN-TOKENS.md` remain the normative token sources.

The direct matrix contains ten existing screen/state captures, each captured in Light, Dark, and System-dark at 390×844, 768×900, and 1440×900: 90 PNGs total. System-dark used a new Playwright context with `colorScheme: "dark"`, no `phx:theme` localStorage value, and the existing system-dark invariants. The route and state remain explicit in every image name and are enumerated below.

The Playbooks empty-state capture used an empty task-local workspace mounted only for the screenshot run. The repository's three tracked example playbooks were preserved. The interaction suite used the worktree's fixture directory through one shared host/container path. Port 4002 was the only published service port; port 4012 and its preview data were not used.

### Shared vocabulary and source corrections

- The shell, page title, route trail, theme preference controls, notices, status text, and focus behavior are shared where their function matches. `OpsUi` supplies reusable controls and semantic groupings; it does not own the six surfaces' task order or domain copy.
- `ops_verdict` and metric surfaces use neutral containers. Status remains in visible wording and local theme-aware cues. Search health retains separate Backend and Queue groups. Playbooks retains workspace, imported-draft, preview, and run-result provenance.
- The Plan 177-01 Task 1 text said the Control Room's real section pattern was an `ops_section/1` call. Source inspection disproved that specific claim: the current implementation uses a labelled native `<section>` and the actual `ops_notice`, `ops_empty_state`, `ops_verdict`, and `ops_intent_card` calls. The guide and catalog describe this rendered source; no fictional call or UI refactor was added.
- The matrix's original Search title locator matched both the page title and “Run a search to see results.” It now uses an exact page-title match. This is a test-harness correction; Search behavior is unchanged.

## Direct visual findings

All ten nine-image contact sheets were inspected in Light, Dark, and System-dark at mobile, intermediate, and desktop widths. The full PNGs are retained under `examples/scrypath_ecommerce/test-results/phase177-before/` and inventoried below. The contact sheets used for inspection were temporary files under `/private/tmp` and are not the evidence source.

- The six distinct scan paths remain visually distinct. The Control Room leads with observed posture and its three routes; Search health separates fleet totals from schema evidence; Failed sync and Sync and drift keep recovery/reconciliation evidence and actions attributable; Search keeps the submitted criteria adjacent to Results; Playbooks keeps an empty workspace, import, preview, and run tasks separate.
- Each theme uses the same hierarchy. System-dark resolves to dark surfaces with the System preference selected and no explicit theme override. Status has visible text; accent remains local to actions, selected navigation, and small status cues.
- The 390px and 768px captures reflow the same evidence and controls into a single-column task path where needed; the 1440px captures preserve readable content widths and the shared navigation frame. The existing executable depth suite separately covers its selected overflow, focus, and interaction assertions.
- The final Playbooks capture visibly shows “No playbooks yet” with Import JSON and Open Search actions. Its empty workspace was isolated for capture; `/tmp/phase177-empty-playbooks` is a temporary test path, not a production configuration claim.
- Search health captures include the short “Search health refreshed” success toast because the existing representative capture prepares the page by clicking Refresh. It is post-refresh feedback, not a permanent page banner.
- No concrete shared-token mismatch or visual defect requiring a UI source correction was found in this baseline. This is a visual/source audit finding, not a claim that every UI-SPEC state has passed implementation verification.

## Acceptance criteria carried forward

The following 48 requirements are copied from `177-UI-SPEC.md` as acceptance criteria for the remaining phase work. Their inclusion here does not mark them passed. The direct-image matrix and selected Search/Playbooks interaction checks are separate evidence classes and cover only the states described above.

| Surface | State | Acceptance criterion |
| --- | --- | --- |
| E1 — Control Room | empty | When allowed schemas or runtime setup are absent, show the existing specific setup guidance; do not represent missing observations as a healthy zero-error posture. |
| E1 — Control Room | loading | Refresh remains tied to the current posture and keeps its in-flight state; do not infer completion from dispatch or briefly show a healthy verdict before observations return. |
| E1 — Control Room | error | Keep the unavailable source, inspected reason, and existing Search health destination visible; preserve any other known posture evidence. |
| E1 — Control Room | populated | Lead with the actual trust verdict and its evidence, then preserve the three distinct intent routes for recovery, pre-promotion verification, and search exploration. |
| E1 — Control Room | partial | Keep known sources and unavailable queue/backend observations separately labeled; never infer overall health from a partial response. |
| E1 — Control Room | overflow | At desktop, intermediate, and narrow widths, wrap full schema/task identifiers and reasons or use existing bounded evidence scrolling; keep controls reachable and avoid document-level horizontal overflow. |
| E1 — Control Room | zero-one-many | Render zero, one, and many configured schemas with truthful counts and grouping; counts alone do not imply search health or successful recovery. |
| E1 — Control Room | long-text | Long schema labels, task identifiers, and diagnostic reasons wrap or reflow with full accessible context; actions retain their text label or accessible name. |
| E2 — Search health | empty | No-schema and missing-runtime states retain the exact configuration guidance; do not confuse unavailable configuration with an empty but healthy fleet. |
| E2 — Search health | loading | Refresh Search health keeps its label, current selection, and busy state together; do not present old observations as the result of an in-flight refresh. |
| E2 — Search health | error | Show each fetch error with its inspected reason and the existing failed-work route; keep independent schema evidence available. |
| E2 — Search health | populated | Show the actual summary verdict and four fleet metrics before the worst-first per-schema signal cards, with Backend and Queue evidence distinct. |
| E2 — Search health | partial | An unavailable queue/backend observation remains explicit beside known values; zero errors or a last success does not imply full health. |
| E2 — Search health | overflow | At desktop, intermediate, and narrow widths, full schema/index identifiers and reasons wrap or use existing bounded scrolling without hiding controls or causing document overflow. |
| E2 — Search health | zero-one-many | Zero, one, and many schemas retain accurate counts, plural wording, and per-schema grouping; order remains worst-first where applicable. |
| E2 — Search health | long-text | Long schema/index names and fetch reasons remain fully readable through wrapping or reflow; error context is not hover-only or clipped. |
| E3 — Failed sync work | empty | Show “No failed sync jobs” only for an observed empty result, with the existing recovery-confirmation guidance; missing schema/runtime configuration remains a separate setup state. |
| E3 — Failed sync work | loading | Keep selected-schema identity, refresh/recovery context, and the in-flight state together; acceptance or dispatch must not imply completed repair. |
| E3 — Failed sync work | error | Identify the selected schema, show the actual failure reason and backend/queue next step, and retain any known failed-job history. |
| E3 — Failed sync work | populated | Keep newest evidence first, distinguish retryable rows from retained history, and show Retry accepted separately from authoritative completion. |
| E3 — Failed sync work | partial | Keep known failed rows attributable while unavailable observations remain explicit; do not replace retained history with a fabricated complete or empty result. |
| E3 — Failed sync work | overflow | At desktop, intermediate, and narrow widths, full job/source identifiers and reasons wrap or use existing bounded scrolling; retry controls remain reachable without document overflow. |
| E3 — Failed sync work | zero-one-many | Zero, one, and many failed jobs use truthful counts and existing row grouping; do not offer retry for an ineligible item or imply all work is recoverable. |
| E3 — Failed sync work | long-text | Long source/job identifiers and failure reasons wrap with full context; errors and action labels remain available without hover or clipping. |
| E4 — Sync and drift | empty | Keep no schemas, no drift, and not-yet-available observations distinct; a missing observation never becomes an empty-success state. |
| E4 — Sync and drift | loading | Preserve separate recovery observation, sync/queue refresh, and promotion in-flight identities; refresh observes accepted recovery and never submits work. |
| E4 — Sync and drift | error | Distinguish a failed drift observation from a remote operation failure; retain the actual reason and the documented safe next step for each. |
| E4 — Sync and drift | populated | Keep sync/queue evidence, contract drift, freshness, operation outcome, and gated promotion visually and semantically separate. |
| E4 — Sync and drift | partial | Keep accepted, running, terminal, unknown, and unavailable observations distinct and attached to the exact task/index identity. |
| E4 — Sync and drift | overflow | At desktop, intermediate, and narrow widths, full schema/task identifiers, timestamps, and reasons wrap or use existing bounded evidence scrolling without document overflow. |
| E4 — Sync and drift | zero-one-many | Use truthful zero/one/many grouping for schemas and operations; counts do not imply repair, promotion, or successful reconciliation. |
| E4 — Sync and drift | long-text | Long identifiers and operation reasons wrap or reflow with the safe next step still visible and the complete accessible context retained. |
| E5 — Search | empty | Keep not-run, successful zero-hit, and unavailable schema/runtime states distinct; a blank query remains a valid exploratory query where the existing contract allows it. |
| E5 — Search | loading | The single Run search action retains dispatched mode, targets, query, and page-size identity with its busy guard; later form edits do not relabel the in-flight request. |
| E5 — Search | error | Show the actual request/validation reason and the documented correction-and-rerun step; preserve partial per-index outcomes and details. |
| E5 — Search | populated | Attribute returned results to the actual submitted mode, targets, query, and limits; keep the Results region adjacent and explicitly labeled. |
| E5 — Search | partial | Expose each returned, zero-hit, and failed index separately with its reason and next step; a failed index does not erase results or become zero hits. |
| E5 — Search | overflow | At desktop, intermediate, and narrow widths, long queries, identifiers, and response values wrap or use existing bounded disclosure scrolling; controls remain reachable without document overflow. |
| E5 — Search | zero-one-many | Show accurate target and hit counts; zero hits remains a successful response, and single/multi-index outcomes remain attributed per index. |
| E5 — Search | long-text | Long queries, module names, index identifiers, errors, and action labels wrap/reflow with full accessible context; no required reason is clipped or hover-only. |
| E6 — Playbooks | empty | Keep an empty workspace distinct from read-only examples, no selected valid preview, and no run yet; each state retains its own existing import/load guidance. |
| E6 — Playbooks | loading | Import, preview, run, save, and file operations retain the current file/draft/run identity while pending; do not announce persistence or completion before it is authoritative. |
| E6 — Playbooks | error | Keep actual import, load, save, or run failure attached to the affected file/run with its correction; leave unaffected catalog work reachable. |
| E6 — Playbooks | populated | Keep catalog management, selected preview, run action, outcome, and Search handoff as distinct tasks with source and submitted criteria attributable. |
| E6 — Playbooks | partial | Preserve per-index partial outcomes and workspace/read-only/imported provenance; missing configuration or permissions never becomes invented ready, saved, or complete status. |
| E6 — Playbooks | overflow | At desktop, intermediate, and narrow widths, filenames, run identifiers, criteria, and diagnostics wrap or use existing bounded scrolling without document overflow. |
| E6 — Playbooks | zero-one-many | Render zero, one, and many files/results with truthful counts and stable row grouping; zero hits is distinct from no run and from failure. |
| E6 — Playbooks | long-text | Long filenames, query criteria, run identifiers, and error reasons wrap/reflow with full accessible context; icon-only file actions keep explicit accessible names. |
