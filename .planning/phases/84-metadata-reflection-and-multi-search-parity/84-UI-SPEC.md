## Interaction Contract

- Capability metadata must render as plain data groups, not generated widgets: `filters`, `sorts`, `facets`, `paging`, `defaults`, and `constraints` each get their own labeled section — source: `META-01`, `META-02`.
- Applied state must always be visually distinct from available state: use filled accent badges for `applied`, muted secondary badges for `available`, and neutral text rows for `unsupported` or absent capabilities — source: Phase 83 visibility carry-forward + Phase 84 parity goal.
- Defaulted values and fixed constraints must never look identical: defaults use accent-outline badges labeled `Default`; fixed constraints use destructive-outline or high-contrast lock styling labeled `Fixed` — source: Phase 83 conflict and inspectability decisions.
- Single-search and `search_many/2` examples must preserve the same reading order: `input summary` → `resolved criteria` → `capability metadata` → `per-entry differences` → `failure boundaries` — source: `MSCH-01`, `MSCH-02`.
- Multi-search screens or docs tables must keep per-entry boundaries visible. Do not collapse per-schema metadata into one blended capability list when entries differ — source: `MSCH-02` and existing `search_many/2` honesty language.
- Error presentation must stay field-scoped and local. Invalid filters, sort values, or fixed-constraint conflicts render beside the affected field/group before any page-level summary — source: requirements + Phase 83 explicit-failure carry-forward.
- Empty states must distinguish `nothing declared` from `declared but not applied`. The first is a capability absence state; the second is a neutral unresolved state, not an error — default derived from requirements.
- Host-owned concerns must be visually called out as non-contract areas: tenant policy, authz, and related-data behavior appear only in muted advisory text blocks labeled `Host-owned` — source: `META-03`, roadmap guardrails, and pitfalls research.
