No fail-open hole was found that can skip a required lane in production. The evidence:

Nothing in the Docker build, the mounted Playwright lane or the five gated Node test files reads `docs/`, a root `*.md`, or `.planning/` (`.dockerignore` already excludes `.planning`; the retired-identity scan and token tests run in the always-run `mix verify.repository_contracts` path; `ui-review.mjs` `sourceIdentity` is a local-only command). ## Warnings

### WR-01: `classify()` drops non-string entries instead of treating them as non-allowlisted

**File:** `scripts/ci/ecommerce_path_classifier.cjs:46-48`
**Issue:** The module's contract is "anything unexpected runs the lanes", but the exported pure function filters out every non-string and empty entry before checking the allowlist. `classify({eventName: "pull_request", paths: [".planning/a", {path: "lib/x.ex"}, 42]})` returns `{run: false, reason: "all-paths-allowlisted"}` (verified by running it). The CLI cannot reach this today, because `changedPathsFromGit` and `pathsFromFile` only ever yield non-empty strings. But `classify` is exported and the test at `ecommerce_path_classifier.test.cjs:99` pins the lenient behavior only for the all-junk case, so a future caller or refactor (for example a JSON paths source) inherits a silent fail-open. An unrecognized entry is evidence the diff was not understood, which is the case this design is meant to run the lanes for.
**Fix:**
```js
const list = Array.isArray(paths) ? paths : [];
const candidates = list.filter((entry) => entry !== "");
if (candidates.length === 0) return { run: true, reason: REASONS.emptyDiff };
// A non-string entry is not on the allowlist: it runs the lanes.
if (candidates.some((entry) => typeof entry !== "string" || !SKIPPABLE_PATTERN.test(entry))) {
  return { run: true, reason: REASONS.nonAllowlistedPath };
}
```
Update the `[null, 7, ""]` case at test line 99 to expect `non-allowlisted-path`, and add `[".planning/a", {}]` as a planted case. The offender lookup in `decide` (lines 163-165) must then stop filtering non-strings too.

## Info

### IN-01: The `ecommerce-mounted` job-level `if:` assertion is unanchored

**File:** `test/mix/tasks/workflow_wiring_test.exs:492`
**Issue:** `assert mounted =~ @mounted_fail_open_if` is a substring match over the whole job block. A commented-out line (`# if: ${{ !cancelled() && ... }}`) or a step-level copy still satisfies it, and the `consumers == 3` count at line 503 also counts a commented line. If the job-level condition were disabled, the lane would always run: safe, but the CI saving would silently disappear and the suite would stay green. `repository-contracts` is anchored correctly (`"\n    if: ${{ !cancelled() }}\n"` at line 526, plus the `^\s+if: ` count of 3 at line 538), so the two jobs are inconsistent.
**Fix:** Anchor to the job-level indentation: `assert mounted =~ "\n    " <> @mounted_fail_open_if <> "\n"`.

### IN-02: No test exercises the real merge-commit shape or an advanced base

**File:** `scripts/ci/ecommerce_path_classifier.test.cjs:157-167`
**Issue:** `makeRepo` builds linear history where `origin/main` equals the branch point. In Actions the checked-out `HEAD` is the `refs/pull/N/merge` commit and `origin/main` may have moved on since. Three-dot semantics are the reason the code uses `origin/<base>...HEAD`, but no test distinguishes it from `..` or other variants: with linear history they return identical names. I confirmed by hand that the current code is right (merge commit, advanced `origin/main`, only the PR's paths reported), so this is a missing regression guard, not a bug.
**Fix:** Add a CLI test that (1) branches `pr` with a docs-only commit, (2) advances `main` and `origin/main` with a `lib/` change, (3) checks out a merge commit of `pr` onto the old `main`, then asserts `run=false`. A two-dot or tip-vs-tip regression would then show up as `run=true`.

### IN-03: Impossible-state guard: base-ref fetch retry under a full-history checkout

**File:** `scripts/ci/ecommerce_path_classifier.cjs:88-100`
**Category:** necessity
**Issue:** `changedPathsFromGit` retries once with `git fetch --no-tags origin <baseRef>` when the first diff fails, to repair a missing `origin/<base>` remote-tracking ref. In the only caller, the `ecommerce-path` job (`ci.yml:423-424`) uses `actions/checkout` with `fetch-depth: 0`, which fetches `+refs/heads/*:refs/remotes/origin/*`, so `origin/<base>` is always present. A missing merge base fails the same way after the fetch, so the retry cannot help there either. This rests on the checkout action's documented refspec rather than anything in the repository, so it is judgment, not proof. The cost is an extra network call on every diff failure, and an unbounded one (see IN-06). The guard is also covered by its own test (`test.cjs:253`), so removal also drops that test.
**Fix:** Drop the retry and let a failed diff go straight to `diff-error` (still `run=true`), or keep it and give it the timeout from IN-06. Record the choice in a comment.

### IN-04: `options.output` is parsed but never read

**File:** `scripts/ci/ecommerce_path_classifier.cjs:104-106, 180-181`
**Issue:** `parseArgs` stores `--output` in `options.output`, but nothing reads it. `main` re-scans `argv` with `indexOf("--output")`, which takes the first occurrence while `parseArgs` takes the last, so the two parsers can disagree on a repeated flag. The comment at line 179 gives a valid reason to find the output file independently of `parseArgs` (a bad argument must still report into the file), but then the `options.output` field is dead.
**Fix:** Remove `output` from `options` and the `takesValue` map's use of it, but keep `--output` in the accepted list so it is not rejected as an unknown argument. Or have `parseArgs` collect leniently and reuse its result in `main`.

### IN-05: The upload-artifact pin check now proves only the pin's form

**File:** `test/mix/tasks/workflow_wiring_test.exs:1667-1685`
**Issue:** The previous assertions pinned the exact reviewed SHA. `assert_upload_artifact_pin!` accepts any 40-hex SHA followed by `# v7` (with optional minor and patch digits), and `scripts/ci/check_action_pins.sh` only checks that a reference is 40-hex. A SHA that is not the `v7` release but is labelled `# v7` passes both. The loosening is deliberate (it stops Dependabot bumps from failing the suite) and tested, but it is a weaker guarantee than before and it is unrelated to the path classifier, so it rides along in commit 87354a32.
**Fix:** Accept the trade-off, but record in the ledger that the SHA-to-tag correspondence is now verified only by review of the Dependabot PR. If a mechanical check is wanted later, resolve the tag with `git ls-remote` in a non-gating scheduled job.

### IN-06: Git subprocesses have no timeout, so a hang delays both required lanes by up to 5 minutes

**File:** `scripts/ci/ecommerce_path_classifier.cjs:64-73, 92-95`
**Issue:** The `git diff` and `git fetch` calls use `execFileSync` without `timeout`. A hung fetch is stopped only by the job's `timeout-minutes: 5` (`ci.yml:420`). Because `repository-contracts` and `ecommerce-mounted` now `needs: ecommerce-path`, a hang holds both required lanes for the full 5 minutes before they start, and then they run anyway (`result != 'success'`). The 5-minute bound is documented and fail-open, so this is a latency cost on a rare path, not a correctness issue.
**Fix:** Pass `timeout: 60_000` (and `killSignal: "SIGKILL"`) to both calls. A timeout throws, which already lands on the `diff-error` branch with `run=true`.
