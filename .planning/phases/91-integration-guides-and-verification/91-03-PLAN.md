## DOMINANT CORRECTNESS RISK — RESOLVER-ARITY DUALITY (read before coding)
The `fan_outs:` resolver MFA is invoked with TWO different first-arg shapes depending on sync_mode:
  - :inline -> owning-schema RECORDS  ([%Author{}])   (lib/scrypath/sync.ex:92)
  - :oban   -> owning-schema DOC IDs  ([author_id])    (lib/scrypath/sync/related_worker.ex:47)
The two existing hermetic tests encode exactly this split (related_test.exs:50 records vs
related_worker_test.exs:60 ids). The example resolver MUST handle BOTH shapes (pattern-match
`[%Author{} | _]` vs `[_id | _]`, funnel both to a reload-by-author_id query) or the :oban path
crashes on a struct it expected to be an integer. D-14 (both smoke paths) is the guard that
proves this — the oban smoke would fail if the resolver only handled records.

## D-15 MECHANISM (adopted): denormalized posts.author_name column
Per RESEARCH Pattern 3, the renamed author's name reaches the Post document via a denormalized
`posts.author_name` column kept in sync by the Blog context inside `update_author/3` (an
`update_all` on Posts by author_id, ordered BEFORE the fan-out), and the resolver reloads affected
Posts by `author_id`. This stays 100% app-owned/explicit and is uniform across both arities
(reload-by-id needs no Author join). The library gains NO preload/association-walking behavior.
