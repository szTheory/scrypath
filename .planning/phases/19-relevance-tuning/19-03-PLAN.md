<!-- Drift comparison shape (verify_applied) -->
Declared (from `resolve/2` + `translate_settings/1`, i.e. wire form) is compared KEY-BY-KEY against applied (fetched via `get_settings/2`). A drift entry is produced when:
- A key exists in declared AND applied AND their values differ, OR
- A key exists in declared but NOT in applied (Meilisearch missing), OR
- A key exists in applied but NOT in declared BUT only if the key is in the recognized Meilisearch-native set (`searchableAttributes`, `sortableAttributes`, etc.). Keys Meilisearch returns by default that Scrypath didn't declare (e.g., default `rankingRules` when Scrypath didn't specify) are NOT drift — the comparison is "declared-subset-of-applied" not "exact match." The `:__unrecognized__` bucket entries follow the same rule as declared keys.

Drift tuple format: `{key :: atom() | binary(), declared_value :: term(), applied_value :: term() | :not_present}`.

       ```elixir
       @doc """
       Reads applied Meilisearch settings via `Client.get_settings/2`, compares key-by-key
       against the declared+translated wire form, and returns drift if any.

       Returns:
         - `:ok` — declared keys all match applied values (declared-subset-of-applied semantics).
         - `{:error, {:settings_drift, [{key, declared, actual}, ...]}}` — one or more declared keys diverge or are missing from the applied settings.
         - `{:error, :index_not_found}` — applied-side index does not exist (Meilisearch 404).
         - `{:error, term()}` — other transport/runtime errors passed through.

       TUNE-05 drift-detection primitive consumed by plans 19-04 (reindex flow wiring) and
       19-05 (`mix scrypath.settings.diff`).
       """
       @spec verify_applied(module(), String.t(), keyword()) ::
               :ok
               | {:error, {:settings_drift, [{binary() | atom(), term(), term()}]}}
               | {:error, :index_not_found}
               | {:error, term()}
       def verify_applied(schema_module, index_name, config) do
         declared_canonical = resolve(schema_module, config)
         declared_wire = translate_settings(declared_canonical)

         case client(config).get_settings(index_name, config) do
           {:ok, applied_wire} ->
             case compute_drift(declared_wire, applied_wire) do
               [] -> :ok
               drift -> {:error, {:settings_drift, drift}}
             end

           {:error, {:http_error, 404, _body}} ->
             {:error, :index_not_found}

           {:error, reason} ->
             {:error, reason}
         end
       end

       @doc false
       # Pure function for testability (mirrors the verify.release_parity compute/2 split).
       @spec compute_drift(map(), map()) :: [{binary() | atom(), term(), term()}]
       def compute_drift(declared_wire, applied_wire)
           when is_map(declared_wire) and is_map(applied_wire) do
         declared_wire
         |> Enum.reduce([], fn {key, declared_value}, acc ->
           case Map.fetch(applied_wire, key) do
             {:ok, ^declared_value} -> acc
             {:ok, applied_value} -> [{key, declared_value, applied_value} | acc]
             :error -> [{key, declared_value, :not_present} | acc]
           end
         end)
         |> Enum.reverse()
       end
       ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `Client.get_settings/2` → Meilisearch HTTP API | Outbound read-only GET. Uses the Scrypath-configured `meilisearch_api_key`. No user-supplied URL segments beyond `index_name`, which is compile-time-validated via the schema contract (not runtime-user-supplied). |
| `Settings.verify_applied/3` → drift tuple | Drift tuples contain declared and applied values. Values could include user-supplied synonym lists, ranking rules, stop words. Most have no confidentiality concern. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-03-01 | Information Disclosure | drift tuple output | mitigate | Drift tuples are returned via `{:error, ...}` tuples. When surfaced in `mix scrypath.settings.diff` output (plan 19-05), they are printed to stdout. They do NOT include the Meilisearch API key or auth headers. The tuple values are settings-shape data only (synonyms, rules) — these are INPUTS the operator declared, not secrets. Low severity, accept risk with documentation. |
| T-19-03-02 | Denial of Service | `verify_applied/3` call on large applied-settings response | accept | Meilisearch applied-settings responses are bounded (< 100 KB typical; the settings surface has a bounded number of keys). `compute_drift/2` is O(n) over declared keys only — declared is always small (5-10 keys). No pathological-input concern. |
| T-19-03-03 | Spoofing | `meilisearch_client:` test injection | accept | The `client(config)` indirection allows test mocks to replace the real client. In production, `config[:meilisearch_client]` is unset and defaults to `Client`. Tests use it; production callers don't. Not a new surface introduced by this plan — pre-existing pattern from `settings.ex:29-31`. |
| T-19-03-04 | Information Disclosure | 404 translation | mitigate | `{:http_error, 404, body}` is translated to `:index_not_found` BEFORE the body reaches the caller. This prevents Meilisearch error-body content (which could include the API URL, headers, or other identifiers) from leaking into operator-facing error output. The raw `body` is dropped at the translation point. |
| T-19-03-05 | Race condition | drift verification window | mitigate | The drift-verification race window between apply_settings→wait→verify is bounded by the `wait_for_task/2` primitive, which polls Meilisearch until the settings task completes. `verify_applied/3` runs AFTER the settings task is complete per the plan 19-04 `with`-chain placement. The window is therefore: settings-task-completed → read-back → compare. No new concurrent writes in this window because reindex is single-writer per target index (v1.3 design invariant). Documented in the relevance-tuning guide (plan 19-07). |

No high-severity threats. The plan adds one GET wire call and one comparison function; no new privileged operations.
