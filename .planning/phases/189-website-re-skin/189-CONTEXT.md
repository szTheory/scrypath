## Implementation Decisions

### Token derivation and role map (SITE-01)
- **D-01:** `website/scripts/build.mjs` reads `brand/tokens.json` and emits `assets/tokens.css`: light values on `:root`; dark values on `:root[data-theme="dark"]` and the same dark set inside `@media (prefers-color-scheme: dark) { :root[data-theme="system"] { ... } }`. There is no second pin file for the site; the brand pin (`mix verify.brand`) already guards the source bytes. `color-scheme` follows the active theme so native controls and scrollbars match.
- **D-02:** The role map in `build.mjs` is the only place a color value may be named. Roles: page, panel, ink, muted, link, edge (hairline), control-edge, sunken, selected, code-bg, code-text, the four status colors, focus, and `on-primary` (light: white, i.e. `light.panel`; dark: Night, i.e. `dark.night`). Each role resolves to a `brand/tokens.json` path. For the two dark roles with no token (`selected`, `control-edge`) it resolves to the `brand.json` `color.contrastPairs` hex it must equal. The build fails when any role resolves to nothing in either theme. (See Open contradictions, item 1: the dark `control-edge` hex is not in `contrastPairs`.)
- **D-03:** Every non-filled button, the picker buttons and any bordered control use `control-edge`, not `hairline` (hairline is 1.3:1 on Page; control-edge is about 3.66:1 light and 5.07:1 dark). The book's rule: an input or a button has a Control Edge border.
- **D-04:** The primary button label uses `on-primary` in both themes (reusing the ink role gives 2.19:1 in dark). The `button` pair from `brand.json` is asserted for the one `.button-primary`, in rest, hover and `:focus-visible` states. Filled buttons use `outline-offset` of at least 2 px.
- **D-05:** Text and fill surfaces use opaque token colors only. `color-mix()` is allowed for borders and shadows. The contrast resolver parses both `rgb()` and `color(srgb ...)` computed forms (Chromium serializes `color-mix()` as `color(srgb ...)`) and composites alpha over the resolved ancestor background. A planted translucent surface proves the resolver does the math. Painting on a 1x1 canvas instead of parsing is an acceptable implementation if it passes the same planted case.
- **D-06:** No color literal in any file under `website/src` (CSS, HTML, JS, SVG). The `<meta name="theme-color">` light value is substituted by `build.mjs` from the role map; `theme.js` sets the dark value from `getComputedStyle(document.documentElement).getPropertyValue('--page')`, never a literal. The no-literal scan covers `theme.js` and the inline diagram SVG.
- **D-07:** `styles.css` is rewritten to variables only: no hex, rgb, rgba, hsl, `color()` or named colors except `transparent` and `currentColor`. Delete the grid overlay and the three gradients (the book allows no gradient). Replace both `text-transform: uppercase` rules. Move to the book scale (display 56 px at wide widths clamped down on mobile, line-height 1.05, tracking -0.02em; heading 28/1.2; body 16/1.55; code 13; label 12; headings in Bricolage 700). No layout reflow of the four pages.
- **D-08:** `diagram.svg` becomes an inline SVG (`{{INLINE:diagram}}` expanded by `build.mjs`) that uses `var(--...)` classes and inherits the site fonts so it themes with the page. If that proves fiddly, replace it with an HTML and CSS flow of five boxes. The old `diagram.svg`, `brand-mark.svg` and `og-image.svg` are deleted.

### Fonts, logo, icons and social meta (SITE-01)
- **D-09:** Fonts are the pinned `display.woff2` (Bricolage, wght 600-800), `ui.woff2` (Hanken, 400-700) and `mono.woff2` (Sometype Mono, 400-500), copied at build time into `dist/assets/fonts/`. Three `@font-face` rules with `font-display: swap`, weight ranges equal to the real subset axes, and CSS-relative `url(fonts/...)` (the stylesheet lives in `assets/`, so it works under `/scrypath/`). Preload only `ui.woff2` and `display.woff2`, each with `crossorigin`. Same-origin only: no CDN, no third-party origin. Bricolage ships.
- **D-10:** `:root { font-synthesis: none }`. Each face gets a metric-compatible fallback face (`size-adjust`, `ascent-override`; copy the pattern at `scrypath_ops/assets/css/app.css:30-33`, including the Liberation and Arimo or Cousine names Linux ships) or the h1 does not use `ch`. One dark display weight is chosen and asserted (the book allows 670 for dark headlines; the subset covers 600-800).
- **D-11:** The three OFL texts are copied to `dist/assets/fonts/` and linked from the footer. The font files and OFL texts the site serves are byte-identical to their `brand.pin.json` hashes.
- **D-12:** Logo: the light and dark lockups as two `<img>` elements, one shown per theme by CSS, `alt="Scrypath"` on the image or its link, width at least 136 px, `flex-shrink: 0`. Drop the `<small>` tagline in the header. Exactly one lockup is visible per theme.
- **D-13:** Icon links: `<link rel="icon" href="favicon.ico" sizes="16x16 32x32">` (the pinned `.ico` holds exactly a 16 and a 32 px PNG), `<link rel="icon" type="image/svg+xml" sizes="any" href=".../favicon-light.svg">`, and the dark SVG under `media="(prefers-color-scheme: dark)"` as an enhancement only (browser support for media-conditioned icons is unproven). The unthemed `brand/assets/icon/favicon.svg` is never copied, linked or referenced (its two paths render black). Every declared icon returns 200; there is no request to a root `/favicon.ico`.
- **D-14:** `og:image` and `twitter:image` are absolute URLs (`{{SITE_URL}}assets/scrypath-social-card-1280x640.png` or the published path of the pinned PNG), with `og:image:width`, `og:image:height`, `og:image:alt`, `og:image:type` and `twitter:image:alt`. Width and height meta equal the PNG IHDR (1280 by 640). Platform cropping is not asserted.
- **D-15:** CSP meta, the first `<meta>` after charset (a meta CSP governs only what follows it): `default-src 'none'; img-src 'self'; style-src 'self'; font-src 'self'; script-src 'self'; base-uri 'none'; form-action 'none'`. No `unsafe-inline`, no `*`, no `frame-ancestors` (unsupported in a meta tag). Safari behavior of the meta CSP is a stated limit, not an assertion.
- **D-16:** Non-ASCII characters in built HTML are a subset of {U+201C, U+201D, U+2019, U+2014, U+2192} (present in all three font subsets; U+00B7 is absent from all three). The scan for color literals excludes HTML text entities such as `&#8217;` (a planted accept case) and covers CSS, SVG attributes, `content=` and `style`.
- **D-17:** The `layout.html` rewrite keeps the strings `https://hex.pm/packages/scrypath`, `https://hexdocs.pm/scrypath` and `{{REPO_URL}}` (`test/scrypath/phase112_contract_test.exs:85-89` asserts them), and the page text the existing contract tests read.

### Theme behavior (SITE-02)
- **D-18:** Default state: `:root` is the light token block and no `data-theme` is hard-coded into any HTML. Dark exists only under `[data-theme="dark"]` and the `system` media block. The picker is three `<button>`s with `aria-pressed` inside `role="group"` labelled "Color theme" (not a radiogroup; no arrow-key handling; document the Tab order: skip link, brand, nav, picker, star, version pill). Targets are at least 24 px (WCAG 2.5.8).
- **D-19:** Picker visibility: the markup ships with `hidden`, `styles.css` contains `[hidden] { display: none !important }` (an author `display` rule otherwise overrides `hidden`), and `theme.js` reveals the picker only after a storage write probe succeeds. With JS off or storage blocked or throwing, the picker is hidden and the page is light. Do not rely on `hidden` alone.
- **D-20:** Storage key `scrypath-theme`. Only `light`, `dark` or `system` are accepted; anything else, or a throwing storage, is light. `theme.js` listens for the `storage` event so a second tab follows. The site is a multi-page site, so a pick persists across pages only while storage works (this is why the picker hides when it cannot).
- **D-21:** `theme.js` is about 1 KB, external, a classic synchronous `<script src>` in `<head>` (no `async`, `defer` or `type="module"`, which reintroduce the flash), no inline script anywhere. It sets `data-theme` before first paint, wires the picker and updates `theme-color` (D-06).
- **D-22:** Forced colors: under `forced-colors: active` the lockup shown follows `prefers-color-scheme` (not `data-theme`), and the pressed picker button differs from the others in a non-color computed property (border width or a check glyph).
- **D-23:** Print: the light token block is emitted again inside `@media print { :root, :root[data-theme] { ... } }` and the light lockup is shown, so stored `dark` prints light ink on white.
- **D-24:** Reduced motion: `scroll-behavior: smooth` is set only inside `@media (prefers-reduced-motion: no-preference)`; `transition-duration` computes 0 s under `reduce` (the current hover `translateY` transitions included). Selection and focus use the brand's 80 ms rule where motion applies.
- **D-25:** Fallback rule (pre-decided, SITE-02): if the picker, `theme.js`, the dark tokens and their browser assertions are not green by the end of plan 189-02 (after one fix cycle, or if the cost would push the phase past 3 plans), ship light-only: drop the picker, `theme.js` and the dark and `system` token blocks, amend SITE-02 and criterion 2 in the phase record, and continue. See Open contradictions, item 2 for the one point where sources differ on whether this pauses for the maintainer.

### Verification rule
- **D-50:** Every success criterion is an executable assertion: the static contract, computed-style and behavior assertions in `check.mjs`, request-and-hash assertions, a LiveView-free DOM check, or hosted CI evidence on the exact head SHA.
