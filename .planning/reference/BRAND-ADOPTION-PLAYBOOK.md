# Brand adoption and UI catalog playbook

A living, evidence-graded record of what works and what does not when a new brand book is applied to an existing UI and the UI is cataloged in a component catalog (phoenix_storybook). It exists so the next rebrand or re-skin, in this repo or a sibling, starts from synthesized lessons instead of repeating them.

**Read this first** when asked to adopt a brand book, re-skin a UI, build a story catalog, or build a copy catalog or copy lint. Scrypath-specific plans live elsewhere (`.planning/research/brand-and-catalog/PROPOSAL.md` during the 2026-11 effort, then the milestone archives); this file holds only lessons that generalize.

## How to keep this file useful

- Every rule carries provenance: where it came from, the file or commit, the date, and how it was checked. A rule without provenance is a guess; mark it `unsourced` or delete it.
- Evidence grade: **V** = verified by running something; **R** = read in code or history, not run; **U** = unverified or inferred; **O** = owner statement.
- Status: **adopted** (we chose it and it held up), **draft** (chosen, not yet tested here), **contested** (sources disagree; the conflict is recorded), **rejected** (tried or advised against, with the reason), **superseded** (replaced; keep the pointer).
- Update in the same change that learns something: when a phase proves or breaks a rule, edit the rule's status and add the evidence. Never delete a contested rule; record the resolution beside it.
- Keep entries short. Link to the commit or file for detail. The change log at the bottom says what moved and why.

### Anti-patterns (do not)

- A logo tournament that a later book replaces (accrue phases 181-182, about 56 commits).
- Expanding thousands of placeholder catalog cases before one real state is proven.
- Putting the brand skin on the storybook shell itself; keep it native.
- Treating inventory completeness as design quality (S3, S4).
- Committing multi-megabyte evidence JSON or per-plan hard-coded evidence directories (C8).
- Updating baselines or tests only to make them green after a deliberate change; replace pinned values from a reviewed mapping and keep contrast thresholds and planted failure controls (T2, T3).

## Checklist for a new brand adoption

1. Commit the book, hash-verified (S1). Record the adoption decision and what it supersedes.
2. Inventory coupling to the old identity (S5) and decide the frozen-names policy (S6).
3. Decide the order (S2); record which evidence you will rely on.
4. Build the token source and both-direction mirror with deny-list and browser check first (T1 to T6).
5. Apply from a reviewed mapping table (T2); keep structural assertions; rewrite pinned values.
6. Set the CI baseline policy before any visual PR (T7 to T9).
7. Prove one whole task, then scale the catalog (S3, C1 to C9).
8. Build the language catalog and literal lint before migrating strings (W1 to W6).
9. Record every deviation and lesson here, with provenance.
