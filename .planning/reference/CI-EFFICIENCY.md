# CI and CD efficiency ledger

Standing rule: [AGENTS.md "CI and CD efficiency"](../../AGENTS.md). Every CI, release, deploy or bot-PR run is looked at for low-hanging speed, iteration-time and cost wins that do not weaken what a check proves. This file is where measured findings, candidates and decisions live. Newest findings first. A candidate is not a decision: apply the low-risk ones in the next CI change, and write the outcome next to the row.

How to measure: `gh run view <run-id> --json jobs --jq '.jobs[]|[.name,.conclusion,((.completedAt|fromdateiso8601)-(.startedAt|fromdateiso8601))]|@tsv'` (skipped jobs have a zero timestamp, filter them out), and `gh run view <run-id> --log-failed` for failures.

## Local-first checklist (before waiting on hosted CI)

1. `mix format --check-formatted <files>` and the one test file you changed.
2. Token and pair tests: `node --test examples/scrypath_ecommerce/ui-tokens.test.mjs scripts/ci/ui_state_pairs.test.cjs` (about 1 s).
3. Package changes: `mix verify.package`. Docs changes: the built-docs contract in `test/release/package_metadata_test.exs`.
4. Static analysis: `MIX_ENV=test mix dialyzer` (about 35 s with a warm PLT; run `mix deps.get` first after a lock change). Found two real errors on 2026-11-20 that the hosted advisory lane had been hiding.
5. Workflow wiring: `act -l -W .github/workflows/ci.yml` lists the jobs (act 0.2.87 at `/opt/homebrew/bin/act`, verified 2026-11-20); `act -j <job> --container-architecture linux/amd64` for the cheap jobs (`backend`, `package`, `core`) with a pinned image that has a working Beam/OpenSSL stack. Not yet measured end to end; record the first real run here. The browser lanes (`ecommerce-mounted`, `ecommerce-e2e`) need the repository's own Docker wrappers, not `act`.
6. A change to anything the verifier fixture copies: run the whole CI Node step locally (`.github/workflows/ci.yml`, "Verify browser build, lifecycle, evidence, and target behavior").
7. A shallow checkout (the `package` job) lacks history: tests that use `git merge-base` or `git show` must handle that (the README header pin test does).
8. **After any merge or rebase that touches a `mix.lock`, run `mix deps.get --check-locked` in the root, `scrypath_ops/` and `examples/scrypath_ecommerce/`** (`scripts/ci/pre_push.sh` does it). The example and `scrypath_ops` depend on each other by path, so Dependabot bumping one lock leaves the other stale. Found 2026-11-21: after #150 merged, #151 failed `ecommerce-mounted` in the Docker build (`Your mix.lock is out of date`) because the example lock still had `dns_cluster` 0.2.0; one `mix deps.get` fixed it, but the push-first path cost a second serialized cycle of about 15 minutes. The check takes seconds.
8. The browser-lane path classifier works offline: `GITHUB_EVENT_NAME=pull_request GITHUB_BASE_REF=main node scripts/ci/ecommerce_path_classifier.cjs --head <ref>` prints `run=false` only when every path changed on `<ref>` over `origin/main` is under `.planning/`, under `docs/`, or a root-level markdown file.
9. After adding or moving any file under `scrypath_ops/test` (including `test/support`) or `lib/scrypath`: `mix test test/mix/tasks/verify_namespace_fence_test.exs` from the root (3 tests, about 1 s). The namespace fence allows `Sigra.` only under the Sigra integration namespace and `scrypath_ops/test/scrypath_ops_web/live/`, and it reads `test/support` too. Phase 190 plan 02 moved a test helper that named the Sigra operator context into `test/support`; the ScrypathOps suite, the wiring test and the node tests were all green, and the first signal was a failed `mix verify.core` about 6 minutes into its unit-test step on 2026-11-20 (the fix was a code change, so both long gates were rerun on the new SHA, about 14 minutes more).
10. The cheap pre-push subset in one command: `scripts/ci/pre_push.sh` (added 2026-11-20). It runs only checks CI already runs: `actionlint` over every workflow, `mix format --check-formatted`, `mix compile --warnings-as-errors`, `mix credo --strict`, `mix verify.workspace_clean`, the workflow wiring and namespace fence tests, and the Node tests for both path classifiers, the BEAM cache planner, the UI tokens and the state pairs. It reports a missing tool as SKIPPED (exit 2), never as passed, and prints the lanes it did not run. It is a filter for cheap failures, not a stand-in for the hosted gate.

## Findings and candidates

1. **An always-red advisory lane hides new reds (found 2026-11-20).** `deep-quality (advisory)` fails on every run because of the known cloak and cloak_ecto advisory, and that masked two new dialyzer errors from Phase 186's brand tooling (`refuse!/1` in `dev/mix/tasks/brand/update.ex`, `fail!/2` in `dev/mix/tasks/verify/brand.ex`: "has no local return"). They had been red since 2026-11-19 with nobody looking. Fixed with `@spec ... :: no_return()` (the same pattern as `verify.release_parity`). Candidate: split the lane so dialyzer and the other deep checks report as their own advisory job and only the dependency audit stays red for the known cause (or make the dependency audit its own job), so the lane is green when only cloak is wrong. Quality gain, small cost change. Status: candidate.

   **Decision (2026-11-21, catalog pre-work): no job split; the step-level separation already exists.** Measured on the CI run for `f6c7991b` (run 44939887715): `elixir scripts/ci/dependency_audit.exs` failed in 12 s, and the next step, "Run deep quality checks independently of the dependency audit" (`run_deep_quality_without_audit()`, guarded by `!cancelled()`), ran after it and succeeded in 2 m 43 s. So a new dialyzer, namespace or no-optional-deps finding turns that step red on its own and is visible in the step list; only the job badge stays red because of the known audit failure. A second job would repeat checkout, setup-beam, cache restore and `mix deps.get` (about 15 s of setup plus a second runner) to improve only that badge, and would require rewriting the two `deep-quality` blocks in `workflow_wiring_test` that pin one job with one audit step. Not worth it. **Revisit trigger:** a new deep-quality red is missed because it hid behind the job badge, or the audit stays red for more than 14 days after the cause is fixed upstream. For the catalog spike, Phase 195 records the new subtree's `mix hex.audit` result by hand, as the v1.49 prep already planned.
2. **Planning-only and docs-only PRs pay the full 19 minutes.** PRs #144 (`.planning/` only) and #145 (README, docs and one test) each ran `ecommerce-mounted` (1134 s) and the whole `repository-contracts` Node step. `ops-ui-path` already shows the pattern: a classifier job and a job-level `if`, so the required context still reports as skipped-green. Candidate: add an `ecommerce-path` classifier and skip `ecommerce-mounted` (and the Node step of `repository-contracts`) when only `.planning/**`, `docs/**`, `*.md` and tests that those lanes do not read changed. Must keep `workflow_wiring_test` passing and must not skip when `brand/`, `scrypath_ops/`, `examples/`, `scripts/ci/` or workflow files change. Estimated saving: about 19 minutes of wall time and about 35 runner-minutes per docs-only PR. Risk low to medium (path list correctness). 

   **Outcome: implemented in Phase 188.1 (this phase's PR), not yet measured on a hosted run.** Status: implemented, saving unmeasured.

   - **Mechanism.** A new `ecommerce-path` job (full-history checkout, then `node scripts/ci/ecommerce_path_classifier.cjs --output "$GITHUB_OUTPUT"`) writes `run=true` or `run=false`. It is an allowlist that fails open: `run=false` only when the event is a `pull_request` and every changed path is under `.planning/`, under `docs/`, or a root-level markdown file. One other path, an empty diff, a diff it cannot compute, any error, and every push, schedule, dispatch or merge-group event gives `run=true`. A rename counts both its old and new path, so moving `lib/x.ex` to `docs/x.md` still runs the lanes. It gates `ecommerce-mounted` (job-level `if`, so the required context still reports as skipped-green) and exactly two steps of `repository-contracts` (the demo dependency install and the browser Node step). `repository-contracts` keeps a job-level `!cancelled()` so a failed classifier cannot skip the required job, and `mix verify.repository_contracts` always runs. Consumers compare with `!= 'false'`, never `== 'true'`, so only an explicit `run=false` from a successful classifier skips anything. No required check was added or renamed (the gate ledger in CONTRIBUTING.md still reads 8 of 12).

5. **Website `build-and-check` install time (measured 2026-11-20, Phase 189 plan 03).** The earlier note (the v1.47 website note, which put nearly all of an eight-and-a-half-minute run in the browser install) does not match recent runs. Measured from the last 30 `website.yml` runs (`gh run list --workflow website.yml --limit 30 --json databaseId,conclusion,createdAt,event`, then `gh run view <id> --json jobs` for each; 28 completed `build-and-check` jobs, one cancelled run and one run with no jobs left out). Every run installs Chromium cold (npm is cached by setup-node). Whole job: median 64 s, p90 175 s, max 407 s. "Install Playwright browsers" step: median 40 s, p90 141 s, max 377 s. One run is over 5 minutes, run 44672719383 (407 s job, 377 s install); the next slowest is run 44674878433 (268 s job, 245 s install). The 12 runs from 02:45 to 04:30 UTC took 50 to 407 s; the 16 runs from 12:11 UTC onward took 32 to 78 s. So the install is about 60 percent of a typical job and nearly all of the tail. **Chosen fix:** one step that uses the runner's Chrome through `SCRYPATH_BROWSER_CHANNEL=chrome` only when `google-chrome --version` succeeds and a one-line Playwright launch probe of the `chrome` channel exits 0, and otherwise runs the known-good `npx playwright install --with-deps chromium`; plus `timeout-minutes: 10` on `build-and-check`, so a hung install ends in 10 minutes instead of the 6-hour job default (the measured max of 407 s fits). **Not chosen:** a cache keyed on the lockfile's Playwright version (adds a cache step, a stale-key risk and restore time, where the runner's Chrome costs no download) and `--only-shell` or dropping `--with-deps` (may miss system libraries, and the failure would arrive late inside the job that is the check). **Known limit:** `check.mjs` falls back to the default Chromium if a channel launch throws, but on a runner that took the Chrome path the default Chromium is not installed, so a late channel failure after a green probe would fail the job rather than reinstall; the probe launches the same channel from the same Playwright, which is why it is the gate for this path. **Revisit when:** the first hosted run shows the probe failing, or the median whole-job time is still over 3 minutes. **After numbers are pending:** cold and warm numbers for the new install path can only come from the first hosted run; they go in the phase record's Post-ship evidence section (`189-PHASE-RECORD.md`, item 3), owner the orchestrator, appended in a `.planning`-only commit after the merge (not a push to the PR branch, which would cost another full CI run). **After (2026-11-20, first hosted runs):** the PR #152 head's `build-and-check` took 62 s whole-job on the runner-Chrome path and the post-merge run 75 s, against the 64 s median and 175 s p90 before. One hosted observation for each, no cold versus warm split. The tail is the thing to watch: the fix removes the install download that made up the slow runs, but two data points do not prove the p90. Status: fix applied in Phase 189 and working on its first two hosted runs.

17. **A flaky required test: the loader backfill key generator (fixed in the 2026-11-20 CI speed pass).** `test/scrypath/loader_backfill_postgres_test.exs:7` (`backend (required)`) failed on PR #154 with `StreamData.TooManyDuplicatesError: too many (10) non-unique elements were generated consecutively`.
