Per D-13 replace the heading `#### (c) Write an arity-safe resolver (the #1 footgun)` and its body (through the paragraph ending "reload from the database by id.") with `#### (c) What your resolver receives`:
- A resolver always receives a non-empty list of current owning-schema records and returns target records, under `sync_mode: :inline` and `sync_mode: :oban`. Inline passes the structs you gave `sync_related/3`; Oban jobs carry document IDs and reload the records with the loader (`preload:` / `search_records/2`) when the job runs (keep the exact phrase "document IDs").
- Keep the `update_author/3` example, and reduce the resolver to the single `[%Author{} | _]` clause mapping to ids and reloading posts. Say existing id-taking clauses are now dead code and safe to remove.
- Triggers that no longer load (deleted, or excluded by `search_records/2`, such as soft-deleted rows) are skipped; if none load, the resolver is not called and the job succeeds. To hide the targets of a soft-deleted owner, sync them directly, for example `Scrypath.sync_records(Post, posts)`.
- Call `sync_related/3` after the write commits; enqueueing inside an open transaction can load stale or missing triggers when the job runs on another connection.
- Inline with a deleted struct still calls the resolver, which usually returns `[]`; an empty trigger list is a noop in every mode.
- Triggers are deduped and sent in jobs of up to 1000; there is no ordering contract (D-03).
- A schema whose `__scrypath__/1` is hand-written (owner-only) keeps working; tenant-scoped owners should define `search_records/2`.
Keep the phrases "durably queued", "records", "sync_mode: :inline", "sync_mode: :oban" and every docs_contract token present. If §(c) is linked by anchor anywhere in `guides/` (grep `arity-safe`), update the link.
