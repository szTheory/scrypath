## Recommendation

Use three progressively stronger layers: public-entry contract checks for library composition, one explicitly named host policy exercised with adversarial database/search rows, and package-backed service assertions only for the configured operations that this workflow actually uses. Reuse the existing Phoenix package harness. Do not create a generalized package matrix to turn every historical OPT-OUT into INTEGRATE.

C-10 must remain split into two claims: Scrypath preserves a supplied tenant criterion through its supported query path; the host authenticates the actor, authorizes membership, chooses the tenant, and scopes any database reads and returned data. A public search option is not an authorization system. The existing ecommerce example lets the visitor select a tenant from URL parameters and deliberately demonstrates filtering across selectable tenants; its receipts cannot establish membership authorization.

C-11 opt-outs are not automatically readiness-critical. Condition 3 concerns important adopter workflows and their actual claims, not endpoint completeness. Configured tenant filtering/settings are prerequisites of a representative SaaS search job and deserve narrow service evidence. Settings readback is a cheap adjacent observation if the harness already creates the index. Facet-value search and multi-search warrant package cases when a concrete important job, existing supported claim, or reproduced defect makes the outcome decision-relevant. This research found two specific source risks that should receive cheap reproduction before either claim is dispositioned as documentation-only.

Do not change the historical v1.39 NOT READY result. A newly dated assessment can cite new evidence and bound remaining claims. This report establishes neither passing implementation results nor an overall readiness decision.

## Who, what, where, when, and why

| Question | Bounded answer |

| Who consumes the API? | Phoenix/Ecto SaaS developers who already own identities, memberships, and business policy; maintainers need reproducible proof of Scrypath's part. |
| What job matters? | An authorized member searches the shared index for their tenant, adds ordinary filters, and receives only allowed records and metadata. Optional facet or multi-index jobs must be separately named. |
| Where is authority? | The host context chooses the trusted tenant after policy checks. Scrypath validates/composes search options and transports the query. Meilisearch evaluates filters. The host controls database hydration and response presentation. |
| When is proof needed? | Before making a new condition-3 claim; invalidate the receipt when projection, option composition, serialization, host policy, package staging, or the pinned service tuple changes. |
| Why this slice? | It exercises a real ownership boundary with discriminatory fixtures, while avoiding a new auth framework or a version/feature cross-product. |

## Specific risks to reproduce before disposition

### C10-R1: tenant option validation may pass while public execution fails

Source chain: [single search](../../../lib/scrypath/search/single.ex), [facet values](../../../lib/scrypath/search/facet_values.ex), and [many search](../../../lib/scrypath/search/many.ex) remove known search keys in `runtime_opts/1` but omit `:tenant_scope`. [Config.resolve!/1](../../../lib/scrypath/config.ex) passes remaining options to runtime validation; `tenant_scope` appears only in the search option schema. Thus successful injection appears followed by an unknown-runtime-option exception. Existing tenant tests stop before this boundary.

**Status:** source-backed suspected defect, not a reproduced result in this report. **Smallest probe:** call public `Scrypath.search/3` with a minimal tenant-declared schema and a recording backend, `tenant_scope: 123`, and an ordinary status filter. Assert the backend is reached and receives both criteria. Repeat only distinct runtime extractors if the first probe confirms the gap; do not add live services to diagnose option validation. A failure here affects a shipped tenant API claim and must be classified before readiness closure. A compatible correction would repair an existing contract; it would not authorize new policy APIs.

### C11-R1: facet-value filter serialization differs from ordinary search

Source chain: public `search_facet_values/4` validates common keyword options, then [FacetValues.run/5](../../../lib/scrypath/search/facet_values.ex) forwards them to [Client.facet_search/5](../../../lib/scrypath/meilisearch/client.ex). That client converts only top-level keys to camelCase and does not render common keyword filters into backend expressions. Its [client test](../../../test/scrypath/meilisearch/client_test.exs) supplies an already rendered list of strings directly to the lower-level client. That test bypasses the public-input boundary. Default options may also be sent to an endpoint with a narrower accepted parameter set.

**Status:** source-backed suspected serialization/endpoint-contract defect, not a demonstrated service rejection. **Smallest probe:** call the public facet API with a valid schema, `filter: [tenant_id: 123]`, and Req.Test; inspect whether encoding reaches HTTP and whether the payload matches the official facet-search endpoint. Test defaults as well as the nonempty filter. If this fails, the material job is tenant-filtered facet vocabulary lookup, an existing capability. A single package/v1.15 case can then establish the repaired real boundary. Ordinary facet distributions and facet-value search are separate claims.

### Host composition boundaries that are intentional

Per-entry override in `search_many/2` is documented composition behavior. Never accept arbitrary per-entry runtime options from a browser and assume a shared tenant option wins. The host should allowlist schemas and options, reject tenant overrides, then attach the trusted tenant to each entry. Likewise, absence of a tenant argument must fail at the host boundary before search; declaring `tenant_field:` does not make every search tenant-scoped. These are host responsibilities unless a specific published library guarantee is contradicted.

## Acceptance candidates for a bounded phase

These are proposed acceptance statements, not completed verification or authorization to implement them.

### Required first: discriminate the library contract

1. **Public tenant entry:** On a schema declaring `tenant_field: :tenant_id` and appropriate `filterable:`, `Scrypath.search/3` with tenant 1 plus `status: "published"` reaches a recording backend with both criteria. Collision and undeclared tenant schema fail before any backend call. Preserve the current error category/raising contract unless an evidence-backed compatibility decision changes it.
2. **Host rejection:** A context receives an explicit trusted actor/scope. Missing scope, no membership, forged tenant selection, and caller-supplied tenant options cannot reach search. If a web route is claimed, use ConnCase to assert rejection and no search invocation; test principal injection is not proof of session authentication.
3. **Host positive and negative oracle:** Persist and index at least tenant A allowed published record, tenant A excluded draft, and tenant B published record with overlapping searchable text and a unique marker. Confirm B is indexed before the negative assertion. A authorized search returns exactly A's allowed IDs and no B markers in hits, returned records, raw results, counts or requested facet values. A legitimate B principal can obtain B, proving the negative was not empty-fixture success.
4. **Hydration boundary:** For a claim including database authorization, perform host-scoped reloading and project the authorized response; check a stale/mismatched search hit cannot expose a newly foreign-tenant database row. If generic `repo:` hydration is used instead, explicitly bound the claim to correctly indexed, stable-tenant rows. Do not label that arbitrary authorization. Never claim record filtering erases raw hit/count exposure.
5. **Input classes:** Cover omitted/empty user filters, normal narrowing filter, conflicting tenant key, quote/backslash-bearing literal, unsupported boolean expression, invalid facet/sort field, and tenant movement or stale projection as an explicit boundary. Use focused examples first; add properties only for a named serialization invariant that examples cannot cover cheaply.

### Minimal C-11 service evidence

6. **Configured settings:** Reuse one package consumer's unique index. Configure explicit searchable/filterable/sortable attributes needed by its job, wait for each task's terminal success with a deadline, and read back that subset. Search a discriminating term, filter mixed rows, and sort deliberately out-of-insertion-order values if sort is claimed. Failure/timeout must fail the scenario with task UID and sanitized error; task acceptance alone is insufficient.
7. **Facet-value API, conditional but now worth reproduction:** Drive `Scrypath.search_facet_values/4` through Req.Test using common public keyword filters and defaults. If a defect is confirmed, add one repaired package/v1.15 case with a string facet and tenant A/B vocabulary. Assert A's expected values/counts and B's absence. A missing/non-filterable facet fails explicitly; never retry unfiltered. This is not a requirement for general autocomplete or UI.
8. **Multi-search, conditional:** Only if an important named cross-schema job is selected, use two tiny schemas with same local IDs/different tenant markers. Host-scope every entry; assert merged hits retain schema attribution, no foreign-tenant hits, and bounded failure behavior. Contract-test per-entry override rejection at the host and native error envelopes. Do not add federation weights, all-schema expansion, or the full error cross-product unless the selected job uses them.
9. **Receipt identity:** Record candidate/final SHA, artifact provenance, Elixir/OTP/Ecto/Phoenix and pinned service tuple, scenario names, positive/negative assertions and lane status. Package proof uses the built artifact; public-registry installation remains a separate release claim. No aggregate green workflow badge substitutes for the particular advisory job result.

## CI, runtime and maintenance economics

Run deterministic public-entry/HTTP-contract checks in the existing fast suite before service proof. Do not copy the entire library suite into the consumer or make a separate job for every acceptance item. Reuse the existing package-staged Phoenix tests, Postgres and Meilisearch containers, index setup, bounded task polling and teardown. A small multi-tenant corpus and one settings application per fixture are enough; no production-sized benchmark is warranted.

Preserve current advisory service-lane posture unless measured instability/risk justifies a separately approved gate change. For milestone acceptance, require the particular job to pass on the exact candidate/final SHA even if the repository workflow permits advisory failure. Log elapsed setup/compile/scenario time to inform later optimization; no runtime estimate here is a baseline. Do not multiply inline/Oban/manual variants for a query-composition claim already independent of sync transport.

Use synthetic tenant IDs, memberships, documents and API keys. Failure artifacts should name scenario, index, task UID and sanitized backend error; avoid access tokens, authorization headers, environment dumps or real document bodies. Deterministic forbidden markers give a stronger leakage oracle than a screenshot and require no UI work.

## Research method, limitations and handoff

Mandatory project/baseline/scope documents and relevant Ecto/Phoenix/system-design/search-library/ratchet prompts were read. The prompts were used as historical design input, not current authority over shipped API behavior. The scope guard and owner's bounded authorization remain authoritative.

The GSD research-plan seam selected Context7 for framework/backend questions and websearch for ecosystem comparison. Neither Context7 tools nor the `ctx7` CLI were available, so official primary pages were fetched with the web tool. Three source digests were persisted through `research-store`; confidence came from the code seam rather than an invented HIGH tier. No Read/Write tool was exposed in this runtime; filesystem reads used `exec_command` and this report used `apply_patch` as the available file-writing tool.

No tests, service runs, dependency mutations or source fixes were executed by this researcher. C10-R1 and C11-R1 need executable classification by the orchestrator before requirements claim a defect or a pass. The old package receipt is run [36000999039](https://github.com/szTheory/scrypath/actions/runs/36000999039), SHA `7931271abe53e83261d85a22077176f75898eb81`, with the narrower historical coverage recorded by Phase 160; it was not rerun here. Current official docs have broader fields/features than that pinned service version and must not silently raise the support floor.

Open decision: choose the smallest named host policy fixture and decide which public outputs it authorizes. Authentication implementation and production policy completeness remain outside the library claim. No new product category or UI/brand deliverable follows from this report.
