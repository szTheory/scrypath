## 2. Strongest case against each note

### A: Discovery and onboarding next
- **Adopter.** There are no external adopters to serve: 4 views in 14 days, zero external issues. Polishing first impressions for an audience of about one is vanity until the numbers move. A's own checkpoint concedes this; the checkpoint is therefore the real recommendation, and Phases 193+ should not be pre-committed.
- **Maintainer.** The "known false instruction" headline is overstated (row 3). Two of four docs are qualified already and a third is a pointer. The honest justification is the README self-links (row 2) and the maintainer's own stated intent (SEED-004, the todo: "reads like AI slop").
- **Contract risk.** A proposes replacing pins with an invariant "no file in `package.files` names a repo-only task" (allowlist CONTRIBUTING and releasing). But `PROJECT.md` "Canonical Adopter Contract" still calls `mix verify.adopter` "the canonical adopter proof spine", and `test/scrypath/docs_contract_test.exs:315-333` and `readiness_contract_test.exs:41,64-67` pin that substring on purpose. The real contradiction is that the adopter proof spine is not runnable by an adopter from the Hex package. A rewritten invariant must be accompanied by an edit to that PROJECT.md contract text, or the check enforces a claim the contract denies. A does not say so.
- **Security.** None material (docs and static site). One footgun: absolute GitHub URLs in a README that the package pins by commit (`README header pin` test, CI-EFFICIENCY item 7) must keep the shallow-checkout handling.
- **DevOps.** Guide-touching PRs pay about 18.5 minutes (`guides/` and `website/` are outside the classifier allowlist); about 7 PRs, serialized by `strict`, is a long milestone for prose.
- **Accessibility.** A website IA redesign checked only by axe, contrast and computed styles proves WCAG mechanics, not comprehension; no real screen reader or Safari (audit "What this does not prove").
- **Product.** Pointing the website's Docs page at HexDocs makes the site thinner exactly when the site is meant to earn stars and serve as portfolio. A flags this as taste; it is the maintainer's call, not ours.
- **Evidence that weakens it:** traffic and issue counts above; the website was re-skinned a day ago (v1.47), so its visual problem is partly solved and the remaining refresh is copy and IA, the least automatable kind of work under the zero-UAT rule.
- **What survives:** the README self-link bug and README length are real, executable-checkable (built-docs self-link scan, link counts, word cap) and cheap; the HexDocs sidebar regroup is a one-file change; the checkpoint design.

### B: Catalog next (4 phases, spike-first)
- **Adopter.** The strongest objection and B concedes it: the catalog serves ScrypathOps, which is not in the Hex package (`scrypath_ops/mix.exs` has no `package:`). No adopter ever sees its output. `PROJECT.md` "Scope Guard" and non-goals list "new UI surfaces" and "no Phoenix UI feature expansion beyond contract-surface clarity" as out of scope; tooling for an unpublished UI sits at the edge of that guard and needs the maintainer's explicit read, not a silent assumption.
- **Core Value.** "Make search indexing feel native to Ecto" is a library promise. The catalog is zero progress on it, and B's own Option 3 (adopter features) is the only candidate that touches it.
- **Maintainer.** B says "the prep is done, ADRs decided", but the ADR 0001 revisit triggers (CI time, NIF, advisory) are exactly what the spike measures, so "ready" really means "ready to measure". The go/no-go rule is good; the milestone is still 8 to 10 plans of internal tooling with a zero-reviewer rule: a catalog that nobody browses-and-judges is worth only its checks (B says this itself).
- **Security.** B's route-absence assertions are sound. The inverted `check_origin` claim (row 14) shows the security prose was not checked against config; the mitigation (dev-only route, loopback publish, prod-absence test) still holds.
- **DevOps.** Adds 9 packages and a Rust NIF to a 54-package lock on a repo whose Actions cache is already over the 10 GB cap (section 1). Cold `ops-ui` was already about 386 s; a NIF fetch inside fresh-graph boundary tests recurs on every eviction. B prices this as "+3 minutes trigger" but not the eviction pressure.

- **CI cost.** C is right: the repo is public and all lanes use the standard `ubuntu-24.04` runner, so there is no per-minute charge. What that changes for the maintainer's stated "GitHub Actions money" concern (AGENTS.md "CI and CD efficiency"): the money cost is zero for the current setup; the real costs are wall time per PR (about 18.5 minutes, multiplied by `strict` serial merges at about 20 minutes each), attention, queue and concurrency limits, and cache eviction (10.76 GB over the 10 GB cap, V). Consequences: drop "runner-minutes saved" as a justification in `.planning/reference/CI-EFFICIENCY.md` (the compat-matrix gating, finding 3, saves nothing that costs money); keep wall-time and flake items; treat cache size and key hygiene as the live "cost"; revisit the statement in AGENTS.md (a maintainer decision: it is a standing instruction, so propose the wording change rather than edit it). Caveats: free minutes apply only while the repo stays public and on standard runners; also, A's and B's estimates in "runner-minutes" should be read as wall time. Also note free does not cover the maintainer's time: B and C-option work should be judged by median PR wall time (C's 20 minute over 10 PRs trigger is a good one).

## 4. Weighing the maintainer's priorities

- **Core Value and adopters first.** Only adopter features (five items in ROLLING-ROADMAP section 6) advance the Core Value directly, and no note recommends them next. They are not ready (API shapes need grilling, per the roadmap), and there is zero adopter evidence they are wanted (no issues, 4 views), which the scope guard and AGENTS.md ("avoid speculative milestone reopening ... without concrete bug or adopter evidence") treat as a reason not to start. Discovery is the nearest adopter-facing work: README and HexDocs are what every future adopter sees, and a broken landing page contradicts the "Operational clarity" and "Release quality" constraints.
- **No human UAT.** B's work is the better match: its output is checks. A's Phases 192-193 are also executable (counts, links, self-link scan, invariant with a planted violation). Only A's website phase is mostly unverifiable prose and IA; that is the phase to make cuttable, scoped to content and IA on the existing tokens, with "not a design review" recorded.
- **Value over procedure.** A full GSD lifecycle for a 3-plan docs fix is disproportionate (A concedes); folding it under a milestone with a checkpoint is the cheapest honest wrapper. B's catalog has the opposite problem: large procedure, value only for the maintainer.
- **Release quality bar.** Favors fixing the landing page before anything else; disfavors releasing a docs-only patch whose content is already in the repo for another month.
- **The open slot.** The maintainer originated the discovery direction (journey doc, SEED-004, README todo) and marked the slot "pending"; the catalog was approved earlier (2026-10-24, 2026-11-19) and is the default. J: the discovery pull is stronger on value and the catalog stronger on checkability and readiness; with traffic near zero, a small, cuttable discovery milestone is the cheaper bet and does not foreclose the catalog.
