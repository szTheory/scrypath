# v1.48 prep A: should Discovery and onboarding be next, and in what shape

Status: research note for the maintainer, 2026-11-20. Recommendation only; no phase plan. Read-only on source: no build, Docker, mix gate, CI run or git operation was run. Labels: V = verified this session by reading a file or fetching a primary source; J = judgment; U = unverified.

## 0. Recommendation in short

Make **Discovery and onboarding** the next milestone (v1.48; the catalog slides to v1.49), but **front-load a docs-truth and README phase that ships alone as a Hex patch release**, and put an explicit checkpoint after it. The website, HexDocs structure and upkeep guards follow as phases 2 to 4 only if the checkpoint holds. Confidence 0.7 for "discovery next, docs-truth first"; 0.55 for the full scope in the journey doc as written. Biggest risk: a visible website redesign that no human may review ships with claims of quality that only computed-style, contrast and link checks can back (section 6, risk 1).

## 1. Facts that drive the decision (all V unless marked)

- **The README is the highest-leverage surface, so README-first is settled by structure, not by guessing traffic.** `mix.exs` sets `main: "readme"`, so the same file is the GitHub front page, the hex.pm page and the HexDocs landing page. Every entry point in `.planning/reference/DISCOVERY-AND-ONBOARDING-JOURNEY.md` except the website passes through it. The maintainer's open question "README-first or hex.pm and HexDocs first" collapses: they are one file.
- **The README has a real link-rot bug on HexDocs.** Fetching `https://scrypath.hexdocs.pm/readme.html` shows the three links to `examples/phoenix_meilisearch/README.md`, `examples/scrypath_ecommerce/README.md` and `scrypath_ops/README.md` all resolve to `readme.html` (a self-link; ExDoc maps any `README.md` basename to the main page). The guide links resolve correctly (`golden-path.html` and so on). On hex.pm the README is client-rendered (the fetch returned a "Loading README" placeholder), so relative-link behavior there is U; a one-time check on the live page is cheap.
- **Sibling libraries link to HexDocs by absolute URL from the README**, never by relative guide paths: Oban (`https://oban.hexdocs.pm/installation.html`), Ecto (`https://hexdocs.pm/ecto/getting-started.html`), Ash (`https://hexdocs.pm/ash`), fetched from their raw READMEs today.
- **Length alone is not the anomaly.** Words in raw READMEs today: Scrypath about 1,480 (`README.md`, 221 lines), Oban 1,214, Req 1,102, Ecto 837, Ash 666, swoosh 1,914, meilisearch-rails 3,778. The problem is structure: 14 sections, a seven-bullet "Choose a route" holding 26 links, and large blocks (Public Surface, Backfill, Drift, Integration smoke, Architecture) that duplicate guides. Oban's shape is the useful pattern: Features, Requirements, Installation, Quick Getting Started, Learning (links out), Community. A target of 600 to 800 words is a judgment (J), not a measured optimum.
- **Hex-shipped docs still name a repo-only task.** `mix verify.adopter` appears at `guides/support-and-compatibility.md:131-132`, `guides/outside-adopter-intake.md:32-33`, `docs/operator-support.md:7`, `docs/jtbd-gap-map.md:78` (and README line 31, CONTRIBUTING, which are acceptable or already qualified). The intake guide and README already say "from a source checkout; not in the Hex package"; the support guide's bullets do not carry that qualifier. `PROJECT.md` "Canonical Adopter Contract" says the published package still contains the task for 0.3.17 and that later releases do not (V: `dev/mix/tasks/`, Phase 183).
- **Contract tests pin the wrong thing.** `test/scrypath/readiness_contract_test.exs:41` asserts the support guide contains `mix verify.adopter`; lines 64 to 67 assert the README and CONTRIBUTING contain it; `docs_contract_test.exs` (1,421 lines) pins `docs/operator-support.md`. Docs-contract surface in total is about 2,240 lines across seven files. Fixing the docs means changing these in the same commit.
- **The website already fixed its own copy of the honesty bug** (SITE-06): `website/src/pages/*.html` has no `verify.adopter`; the home page shows `mix scrypath.status`. But its "Docs" page is 14 `{{REPO_URL}}/blob/main/guides/...` links (GitHub markdown at `main`, which may be ahead of the released package) and the only HexDocs link is the footer (`website/src/layout.html:73`). The site is four pages, about 2,050 words.
- **Audience size is tiny and unmeasured.** hex.pm shows 19 versions, 1 dependant (fetched); the repo has 0 stars (`website-refresh/01-goals-audience-scope.md`, V by `gh api` then). Entry-point proportions in the journey doc are the maintainer's guess.
- **CI cost.** The path classifier allowlist skips the browser lanes only when every changed path is under `.planning/`, `docs/` or a root `*.md` (`scripts/ci/ecommerce_path_classifier.cjs`, `SKIPPABLE_PATTERN`). A README-only PR is cheap (about 7 min per the `CI-EFFICIENCY.md` estimate). Any PR touching `guides/`, `website/`, `mix.exs` or `test/` pays the full roughly 19 minutes (`CI-EFFICIENCY.md` finding 1 and 2), and `website.yml` also runs on `README.md`, `guides/**`, `docs/**`, `mix.exs`. Nothing under `examples/scrypath_ecommerce` or `scripts/ci` reads `guides/` apart from the classifier's own tests (V by grep); `scrypath_ops/test/.../security_test.exs` and `dev/mix/tasks/verify.release_parity.ex` do, so extending the allowlist is a measured-candidate, not a free change.
- **Release engineering.** `package.files` in `mix.exs` ships `README.md`, `guides`, `docs/{jtbd-gap-map,releasing,operator-support,search-backend-sre,local-demo-docker-dx}.md`, `CONTRIBUTING.md`, `ARCHITECTURE.md`. Every one of those changes (and `groups_for_extras`) reaches hex.pm and HexDocs only through a Hex release (the maintainer's explicit yes; 0.3.19 was a branding-only precedent: about 19 min PR CI plus about 3 min publish). The website deploys on merge to `main` with no release. This asymmetry is the main sequencing constraint: a website that points at HexDocs shows only released truth; a website that points at `blob/main` shows unreleased truth.

## 2. Options considered

### Option A: the full discovery milestone as scoped in the journey doc
README trim, website refresh (Home, Evaluate, Operate; Docs to HexDocs), HexDocs sidebar and guide structure, one-owner-per-claim, upkeep guards, all in one milestone.
- Pros: one coherent journey designed once; surface jobs decided together; avoids shipping a README that the site then contradicts. Matches the maintainer's stated preference (journey doc, "recommended"). The brand tokens, deploy smoke and static contract are fresh (v1.47).
- Cons: biggest verification and review surface; the website redesign is visible UI with no human reviewer allowed; touches about 2,240 lines of contract pins and 26 guides (about 37,000 words in `guides/` and `docs/`); the README improvement waits on the whole milestone before any Hex release.
- Footguns: designing all surfaces before fixing the known-wrong text delays the cheapest, highest-certainty value; "restructure guides" has no natural stopping point (26 guides invites endless merging).

### Option B: small docs-truth milestone first
Fix the four docs, invert the contract pins, trim the README (and fix its HexDocs link rot), release 0.3.20, then plan the website refresh.
- Pros: smallest, almost fully executable-verifiable; fixes the only known false adopter instruction; README classifier path makes README-only PRs cheap; ships value with a release the maintainer already handles; honest, low-risk.
- Cons: as a standalone milestone it is about 2 to 3 plans (milestone overhead is disproportionate: audit, archive, planning churn); trimming the README before the surface jobs are decided risks a second rewrite; the site and README would be briefly out of step.
- Footguns: "trim" decided by feel (the todo says AI slop) without an owner map re-creates duplication; rewriting `readiness_contract_test` assertions to green rather than replacing them with a stronger invariant weakens what the check proves.

### Option C: catalog milestone first (the existing v1.48 plan)
phoenix_storybook spike, fixtures, pilot (ROLLING-ROADMAP, "Post-v1.46 proposal").
- Pros: already prepared (about 11 plans); makes the maintainer's own UI work faster; no dependency on a release.
- Cons: ScrypathOps is not in the Hex package (`README.md` says so), so adopters never see the catalog's output; adds 9 packages and a Rust NIF to the 54-package `scrypath_ops` lock (ROLLING-ROADMAP); does nothing for the 0-star, first-impression problem. Under the value-over-procedure principle it earns less per plan than discovery.
- Footguns: the catalog's copy lint would need the same glossary/voice decisions the discovery work settles, so doing it first risks re-linting later.

### Option D (recommended): Option A, with Option B as its Phase 1 and a checkpoint
One milestone, but Phase 1 is exactly Option B and ships (Hex 0.3.20) before the website work starts. Phases 2 to 4 are the website, the HexDocs grouping and the guards.
- Pros: gets the certain value (truth, README) out first; one milestone boundary and audit instead of two; the checkpoint lets entry-point signal (section 5) change scope for free; keeps the "journey designed as one" intent because Phase 2 starts with the owner map.
- Cons: Phase 1 trims the README before the website's Home copy exists, so one small README pass may follow in Phase 3 (budget it: one plan reserve).
- Tradeoff: slightly more planning overhead than B, much less risk than A.

## 3. Lens notes

- **OSS maintainer and adopter, first run.** A newcomer on GitHub or hex.pm sees a logo, four badges, a sentence, a website link, an install block, then "Start here: Golden path", then a 26-link route list (`README.md:15-35`). The golden path (`guides/golden-path.md`, about 870 words) needs Docker Meilisearch from `examples/phoenix_meilisearch/`, config, schema, context, and an IEx check. The README's first code block is a schema, not a search result; the first `Scrypath.search/3` appears about 70 lines after the first code block (README line 126). Time to first search is a function of Meilisearch setup, which the README does not state up front. Honest limit to show early: Meilisearch is required and eventual consistency applies.
- **Product and positioning.** The fit/non-fit text exists twice (README "When Scrypath Fits/Does Not", `website/src/pages/evaluate.html`) plus a third time in guides. This is the strongest asset (honest limits); keep one owner. With 0 stars, no counters, no testimonial, no benchmarks; proof means a real run (Mix output, the example app) not claims. Do not invent comparisons; a named-competitor page needs every fact sourced, and is deferred (J).
- **Content design and UX writing.** Voice per `brand/BRAND.md` and the glossary: say "queued" and "searchable", not "accepted work"; `index.html` still carries "application folklore" and other voice-breaking phrases (`website-refresh/01` section 1.4, partly stale). Link lists: one primary next click, at most three onward links on the README. Use the `ux-writing` skill, checked against `copy_rules.json`-style forbidden words, not against taste.
- **Information architecture.** Diataxis-style modes (tutorial, how-to, reference, explanation; diataxis.fr) map onto what exists: Golden path is the tutorial; most guides are how-tos; `meilisearch-concepts`, `sync-modes-and-visibility` are explanation; API is ExDoc reference. The HexDocs sidebar (`mix.exs` `groups_for_extras`) has "Getting Started" with 14 items, "Operations" 8, "Phoenix" 6, "Maintainers" 5. A 14-item first group defeats grouping. Regrouping is a one-file change with zero content edits. `guides/overview.md` (584 words, a 22-row table) duplicates the sidebar and is itself a link farm; the sidebar is the index.
- **Accessibility.** Website: the static contract and `check.mjs` already run contrast, computed styles and an axe pass on Chromium (v1.47 audit). Not covered: Safari, real screen readers (audit "What this does not prove"). For README: alt text on the header image exists; keep descriptive link text ("Golden path", not "here"); avoid emoji-only headings. For a redesign: keep no-JS complete, skip link, focus styles, 12px floor (existing invariants).
- **DevOps and CI cost.** See section 1. A docs-only milestone is cheap only if its PRs stay under `.planning/`, `docs/`, root `*.md`. Phase 1 necessarily touches `guides/` and `test/`, so budget about 19 minutes per PR (3 PRs, about an hour of wall time if serialized). Candidate (measure first, ledger entry in `CI-EFFICIENCY.md`): add `guides/` to the classifier allowlist for the browser lanes only after confirming `ops-ui`/`core` still run on it; the saving matters because this milestone is guide-heavy. Also the website lane reruns on every README, guides, docs and `mix.exs` change (about 64 s median, finding 5): acceptable.
- **Release engineering.** Phase 1 content needs 0.3.20 (docs-only patch; Release Please PR needs the close-reopen or `gh pr update-branch` nudge; maintainer's yes; per-release about 25 minutes elapsed). Website phases need no release. A HexDocs-only republish exists in Hex but this repo's flow is release-please; do not add a second path (J).

## 5. Signal without analytics (answers the open question)

GitHub's repository traffic data (referrers, popular content, clones) keeps only 14 days (GitHub docs, "Viewing traffic to a repository"), so it is time-sensitive: the maintainer can record `gh api repos/szTheory/scrypath/traffic/referrers` and `.../traffic/popular/paths` today and again at the checkpoint for free. Hex download counts are public (`https://hex.pm/api/packages/scrypath`). HexDocs has no analytics for maintainers (U). Add one optional "How did you find Scrypath?" line to `.github/ISSUE_TEMPLATE/outside-adopter-evidence.md`. With a 0-star, 1-dependant audience the numbers will be small; use them only to break a tie (for example if almost nobody reaches the website), never to justify a redesign.

## 6. What could go wrong

1. **Visible UI with no human reviewer.** The website redesign is subjective by nature. Standing rules allow squash-merge on green and forbid simulating a reviewer. Mitigation: gate only on computed-style, contrast, link, copy and axe checks; publish captures in the PR as nonblocking and labeled "not a design review"; keep the design system and layout components from v1.47 so the change is content and IA, not new styling. Residual: a generic-looking site passes every gate. Accept and say so.
2. **Drift between README, website and HexDocs.** README ships on release; the website ships on merge; HexDocs on release. If the website links to `blob/main`, it describes unreleased code. Fix by linking HexDocs and keeping one owner per claim. Footgun: the website path filter also fires on README and guides changes, so deploys happen without a release; fine, because the site then links only to released docs.
3. **Duplicated content.** The fit/non-fit text, the schema snippet, the sync-mode summary and the install line each live in 3 or 4 places. Without a snippet-parity test the owner map is a wish. Guard with data, not discipline.
4. **Link rot.** Found already (`readme.html` self-links). `blob/main` links break when files move; HexDocs links break when extras are renamed. A link checker that asserts built targets exist is needed before restructuring. Do not rename guide files in this milestone (filenames are HexDocs URLs).
5. **Claims outrunning evidence.** "Time to first search" cannot be claimed without a measured run; the existing `examples/phoenix_meilisearch/scripts/smoke.sh` proves the example path, not a newcomer's. Do not write "in five minutes" anywhere.
6. **Contract-test churn.** About 2,240 lines of pins. Replacing a pin with a weaker one to get green is the named failure. Phase 192 must start with an inventory: which assertions pin a claim and which pin wiring, and the old assertion's intent carried into the new check.
7. **Scope creep on 26 guides.** Cap: no merges, deletions or renames; regroup only. Any merge needs adopter evidence (the AGENTS rule against speculative reopening).
8. **CI cost and slow loop.** Guide-touching PRs pay about 19 minutes; the skip path of the classifier has not been observed on a hosted docs-only run yet (v1.47 audit tech debt). Run the cheap checks locally first (README and link checks, `mix format --check-formatted`, `node --test` for website, `mix verify.package`).
9. **The README trim breaks HexDocs.** The README is HexDocs `main`; HexDocs relative links work for guides, not for repo paths; keep guide links relative or absolute-HexDocs consistently, repo paths absolute GitHub. Test on the built `doc/` output.

## 7. Confidence and what would change the recommendation

- 0.7: discovery next with docs-truth first. 0.9 that the docs-truth fix itself should happen now regardless. 0.55 that phases 194 and 195 should be scoped as above before the checkpoint data exists.
- Choose **B alone** (then return to the catalog) if the maintainer would rather not review any website redesign, or if the checkpoint shows the website gets almost no visits (then the README and HexDocs carry the journey and the site stays a stub).
- Choose **C first** if a catalog-dependent deadline appears (for example ScrypathOps becomes a published package, which would make adopters see it), or if the maintainer wants the adopter features (testing kit, highlighting) before more polish; none is stated.
- Choose **A as one block** only if the maintainer prefers one release at the end over an early 0.3.20.
- Revisit if a library bug or a concrete adopter report arrives (it outranks all of this under the scope guard in `PROJECT.md`).

## 8. Adversarial pass against the recommendation

- *"The audience is 1 dependant and 0 stars; polishing discovery is vanity."* Strongest objection. Partly survives: it argues for keeping scope small and ending at the checkpoint with real numbers, which Option D does. It does not argue for the catalog, whose output adopters never see. What survives: Phase 192 (false instructions, broken links) is justified at any audience size; Phases 194 to 195 are conditional.
- *"README trimming before the website exists makes two rewrites."* True. Survives with one reserved plan; the alternative (waiting) leaves a known false instruction and broken links on hex.pm for another milestone.
- *"A docs-only Hex release is ceremony."* The release is the only way adopters see the fix; 0.3.19 shows it costs about 25 minutes of waiting and one yes. Survives.
- *"Pointing the website at HexDocs makes the site a thin pointer and hurts the portfolio goal."* Real tradeoff: the site then has fewer own pages. Mitigation is that Home shows a real run and honest limits (the content HexDocs cannot give). Survives, flagged as a maintainer taste call (J).
- *"The one-owner rule is unenforceable at 26 guides."* Mostly true; enforce only where mechanical (snippets, install line, forbidden phrases, links). Survives as a narrowed GUARD set.
- *"Replacing pins with an invariant is exactly weakening what a check proves."* It changes what is proven (from "the doc names the task" to "no shipped doc names a repo-only task"), which is the stated contract (`PROJECT.md` Canonical Adopter Contract). Survives only if the new test is shown to fail on a planted violation (add that planted-diff test), as the classifier tests do.
- *"No human reviewer means a redesign is reckless."* Survives as the top risk, bounded by content-and-IA-only scope and by saying plainly what is unproven.
- *"Ash's README is a link farm and thrives."* A large framework with a topics index differs from a 1,400-word library; Oban, Ecto and Req link out sparingly. Does not change the recommendation.
