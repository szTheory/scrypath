## 1. Recommendation in short

1. **Do the readiness pass first (candidate 3), but as one session of housekeeping, not a milestone.** Close v1.48 (audit, complete, archive), then fix the small carry-forward items listed in section 5. It needs no maintainer yes except where marked.
2. **No Hex release now.** Nothing releasable is merged: every commit since 0.3.20 is typed `docs:` or `chore:`, so Release Please has no PR to open, and 0.3.20 shipped yesterday. The HexDocs regroup rides the next release. Time-box: release by 2026-12-21 at the latest, or sooner on a trigger (section 6). The maintainer's explicit yes is needed only when that release PR is merged.
3. **Then v1.49 is adopter features (candidate 2), narrowed and cuttable, behind one API-grilling session. The catalog (candidate 1) moves to "deferred with named reopen triggers", not cancelled.** Reason in one line: it is the only candidate that advances the Core Value, the catalog serves an unpublished UI and sits at the edge of the PROJECT.md scope guard, and the catalog adds a Rust NIF and nine packages to a cache that is already over its cap.
4. **If the maintainer will not do the API grilling, or note B finds no feature with a reason to exist beyond "someone might want it", fall back to candidate 4 (maintenance mode)**, not to the catalog. AGENTS.md already says an idle train is stated plainly rather than filled. This is the main thing note B can flip.
5. **Write down a cadence rule** (section 6) so the 3-patches-in-3-days burst of 2026-11-19 to 11-21 is not repeated: release on library behavior change, a security advisory in a runtime dependency, or an adopter-facing doc defect; never docs-only alone; at most one release per 14 days unless it is a bug or security fix.
6. **The thing that actually moves a 0-star reality is outside this repo**: someone being told it exists. That is a maintainer action (an Elixir Forum post, ElixirWeekly), best done after the first release that carries a real adopter-facing feature. Recorded as an option for the maintainer, not work for agents.

Confidence 0.6 for the whole shape (readiness pass, no release now, adopter features before catalog). 0.8 for "no release now". 0.7 that the catalog should not be next. 0.5 that adopter features beat maintenance mode, which is the part that depends on note B and on the maintainer's appetite for API grilling.

## 4. Lens notes

**OSS maintainer, burnout and cadence.** The risk here is not the agent time, it is the decision queue the maintainer carries: every milestone ends in a closeout, a maintainer decision and a release yes. Over the last 30 days the repo closed v1.46, v1.47 and (almost) v1.48 and shipped three releases. A breather rule costs nothing: after each milestone close, one idle session with housekeeping only and no new milestone until a prepared recommendation exists (already the practice). Recommended extra: cap the next milestone at about 5 plans and one cut line, so a wrong guess costs one PR, not eleven. Compare libraries with solo or small maintainers and real use: Waffle and scrivener_ecto release about three times a year; Req and Oban about monthly. None of them release on three consecutive days except for a regression fix. Anti-pattern from that: using the Hex release as the "done" signal for every docs PR.

**DevOps and CI cost.** Free minutes mean cost is wall time plus cache. Two cheap, measured findings: the 10.74 GB cache over a 10 GB cap (GitHub evicts oldest first, so effects are cold builds after churn; 7.3 GB of it is `beam-v1`), and the release PR running 14 minutes of browser lanes for a version-line diff. Recommendation: do not build the release-PR classifier now. At the cadence in section 6 (about one release a month) it saves under 15 minutes a month, and the classifier would need a test plus a check that nothing in `examples/` reads the package version. Revisit only if releases return to weekly. Cache: measure which `beam-v1` keys dominate and whether the per-branch copies (4.2 GB on non-main refs) can be dropped; a 30-minute look, record it in the ledger, and do it before any milestone that adds a dependency subtree (the catalog). The AGENTS.md "GitHub Actions money" wording stays the maintainer's to revisit; the facts are already in the ledger.

**Release engineering.** Three points. (a) Mechanics: `docs:` and `chore:` do not open a release PR, so deferring a docs-only release is the default state, not a decision to hold something back. To release docs alone you would have to contrive a `fix(docs):` commit. (b) Patch versus minor: `bump-patch-for-minor-pre-major: true` means features ship as patches. 0.3.18 shipped real behavior changes (loader routing for backfill and reindex, id bounds, new telemetry) as a patch with upgrade notes, and the README install line `~> 0.3` accepts any later 0.x. The Elixir guidelines call pre-1.0 versions "no guarantees" and suggest depending on the full patch version. For adopters the safe reading of this repo is therefore "every release can change behavior", which is the opposite of what the README promises ("follows semantic versioning for its public API"). Recommendation, decided at v1.49 opening, not now: ship the first new-public-API release as 0.4.0 (a `Release-As: 0.4.0` footer or `release-as` for one release, remove it after), keep patches for fixes and docs, and then consider moving the install line to `~> 0.4.0` so patches are the only automatic updates. The install-line guard and the minor-bump steps in `docs/releasing.md` (added in Phase 193) already anticipate the move. (c) What 20 releases in seven months signals: to a skimming adopter, a registry page with three versions in three days reads as churn or as automated publishing, and `mix hex.outdated` pings every adopter each time. Good mitigation already exists: the 0.3.19 and 0.3.20 notes say "No library behavior changes in this release". Keep that line, but the better fix is fewer releases.

**Product.** The checkpoint reads nil traffic. That argues against more polish of surfaces nobody visits (catalog, website) and for something an adopter could notice: a testing kit or the reindex and backfill tasks. It also argues for restraint: with no demand evidence, the first adopter-feature phase should pick the one item whose justification is independent of demand (note B decides). A concrete product check available without users: run the golden path from a clean machine as a stranger would and time it to first search; a script that does this in CI is the closest thing to adopter evidence this project can produce. (U: whether the existing `verify.adopter` lane already does exactly this from a source checkout; the support guide says it is not runnable from the Hex package, which is itself the gap.)

**Security and supply chain.** The base is already strong (SHA-pinned actions, read-only default token, secret scanning with push protection, alerts on, zero open alerts). Cheap and valuable additions: (1) turn on Dependabot security updates in repo settings (reported `disabled`; a one-click maintainer setting, a repo-settings change so it needs a yes); (2) make the sigra fix, either in sigra (make `cloak_ecto` optional, the maintainer owns it) or by splitting the `deep-quality` lane so dialyzer is separate from the audit; (3) record in `docs/releasing.md` that a runtime-dependency advisory is a release trigger (0.3.18 already did this for ecto, plug and phoenix_html); (4) confirm Hex account 2FA and the scope of `HEX_API_KEY` (docs say it is scoped to the publish workflows; U: the key's own permissions). Not recommended now: SBOM or provenance work, which has no consumer at this size.

**Brand and positioning.** The claim "Ecto-native, operationally honest" is carried by README and HexDocs, both just rewritten. A feature release that adds `Scrypath.Testing` strengthens it; a catalog does not, because the audience never sees it. A burst of releases with docs-only notes weakens the "release quality" posture a little. The brand identity is adopted and checked; nothing here needs more brand work.

**Pre-1.0 stability promises (patterns).** Good pattern: Oban and Ecto state support floors and deprecate before removing; Req uses 0.x minors for changes and publishes `rc` builds before bigger moves (its latest is `0.8.0-rc.0`, 2026-08-18, per hex.pm). Anti-pattern: promising semantic versioning while shipping behavior in patches under `~> 0.3`. A short "while below 1.0" paragraph in the support guide (what a minor means, what a patch means, how long a deprecation lasts) would cost one doc edit and is the cheapest stability promise available. Candidate for the first phase of v1.49, or for the readiness pass if the maintainer wants it sooner.

## 6. Cadence rule and release triggers (proposed text for `docs/releasing.md` and ROLLING-ROADMAP)

- Release when one of these is true: (1) a library behavior change or new public API merged; (2) a published advisory affects a runtime dependency or Scrypath itself; (3) an adopter reports a doc or packaging defect that the Hex page or HexDocs shows; (4) the maintainer wants to announce.
- Do not release for docs-only reasons unless trigger 3 applies. Docs on `main` and HexDocs converge at the next release.
- At most one release per 14 days, except for a bug fix, a security fix or a broken release.
- Time-box for the pending regroup: if none of the triggers fires by 2026-12-21, release it as `fix(docs):` with a hand-edited "No library behavior changes" note (the 0.3.19 and 0.3.20 pattern). The maintainer's yes is needed to merge that release PR. The 30 days replaces the earlier 45-day figure, which was an invented number.
- The next release that carries a new public API ships as 0.4.0.
- Bot release PRs get no CI until a human-authored event: close and reopen, or `gh pr update-branch` (existing rule).

Catalog reopen triggers (any one): ScrypathOps is published as a package; two or more ops UI regressions in a quarter that the existing token, copy and e2e checks missed and that a catalog would have caught; the phoenix_storybook spike measured under about 3 minutes added cold CI and under one day of CSS work, and the maintainer wants the engine before more adopter work (the D note's swap trigger); an adopter or contributor asks for a browsable component reference.

Maintenance-mode exit triggers (if option 4 is chosen): an outside issue or PR, a referrer that repeats, a dependency advisory, or four weeks passing without any of these (then re-run the checkpoint and decide again).

## 7. Adversarial pass

- **"The catalog is approved, prepared and automatable; you are swapping an approved item for an unprepared one."** Fair. The approvals predate the checkpoint, and the maintainer owns the call. What survives: the catalog's prep is "ready to measure" (D's own phrase), and its payoff is internal. What does not survive: any claim that features are "ready"; they need grilling first, which is why the recommendation puts the grilling in front and names maintenance mode as the fallback rather than silently starting the work. If the maintainer says "the UI is the product and the Hex library is the supporting cast", the catalog wins and this note is wrong about the premise, not the evidence.
- **"No evidence for any feature, so option 4 dominates."** Strong. With 5 unique visitors a fortnight, nothing can produce demand evidence without distribution, and waiting is itself a decision to stay at zero. The reply is that a bounded, cuttable feature phase costs little and gives a release worth announcing; but if note B shows no item with an independent reason (for example the testing kit solving a problem the maintainer's own demo apps hit), flip to option 4 plus distribution.
- **"Releasing the regroup now costs about 25 minutes of CI and one yes, and keeps HexDocs consistent with the README, which is already live."** True, and the README and overview are currently out of step on the live site. But the live audience is about five people, a release still needs a contrived `fix(docs):` commit, and the inconsistency is one sidebar. If the maintainer is about to announce or post anywhere, release first; that is trigger 4.
- **"A 14-day minimum between releases will delay a real fix."** The rule has an explicit exception for bug, security and broken-release fixes.
- **"Moving to 0.4.0 breaks everyone on `~> 0.3`."** Yes: `~> 0.3` admits 0.4.0 today. That is the argument for deciding the install-line shape and the minor policy before the first feature release, and for keeping the next minor small and well documented in upgrade notes. U: whether any outside dependant is on `~> 0.3`; hex.pm does not say. The one known dependant could be asked.
- **"Housekeeping that is not a milestone skips the GSD lifecycle the maintainer values."** The items are small and independent; the milestone-closeout steps (audit, complete, archive) are lifecycle already. Two or more of them touching `scrypath_ops` or `lib/` can be folded into the first v1.49 phase if the maintainer prefers a cleaner paper trail.
- **"The `posture.ex` bug is trivial; do not spend a CI cycle on it."** Agree on priority; the recommendation is to batch it, not to cut a PR just for it.
- **What would flip the recommendation:**
  - Toward the catalog: a published ScrypathOps, a quarter with recurring UI regressions, or a cheap spike result.
  - Toward maintenance mode: note B finds no feature with an independent justification, or the maintainer declines the API grilling.
  - Toward an immediate release: any outside report, a runtime dependency advisory, or a decision to announce.
  - Toward a longer readiness pass: the `mix verify.release_parity 0.3.10` check fails (a real release-engineering defect) or the sigra fix turns out to need work in the sibling repo.
