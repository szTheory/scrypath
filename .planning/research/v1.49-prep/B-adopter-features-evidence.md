# v1.49 prep B: adopter features, or something else on the library side?

Status: research note for the maintainer, 2026-11-21. Recommendation only. Read-only: file reads, `grep`, and four public doc fetches. No git writes, no test suite, no CI. V = verified this session by reading code, a doc or a fetched primary source; J = judgment; U = unverified.

## 1. Recommendation in short

**Do not open the five-feature adopter milestone as sketched. Open a small, cuttable "Adopter-ready" milestone as a labelled strategic product decision (not as evidence-driven work), with this order:**

1. **Fix a false claim and write a "Testing your app" guide using only what is already public** (`req_options: [plug: {Req.Test, ...}]` plus the Oban test helpers). No new API. Add a fresh-consumer walk (an agent builds a throwaway Phoenix app from Hex 0.3.20 using only HexDocs, tests included) to rank what hurts. Treat that walk as maintainer-side friction evidence, not as outside-adopter evidence.
2. **Highlight and crop passthrough** through the existing `per_query` allowlist (additive, same pattern as the ranking-score keys). Only if the walk or the maintainer says search results need it.
3. **`pagination.max_total_hits` as a declared setting plus a paging guard.** Optional; cut line here.

**Defer, with reasons below:** a public `Scrypath.Testing` module (it promotes the internal backend seam, costly to reverse), the `search_indexable?/1` predicate (a workaround exists and the semantics need a real grilling), and `mix scrypath.backfill` and `mix scrypath.reindex` (partly shipped as `mix scrypath.reconcile --action ...`; a thin wrapper that does not work in releases).

**Confidence 0.55** that this beats the alternatives (0.15 full five-feature milestone, 0.15 catalog foundation as already queued as CAT-01, 0.10 idle "silence lane", 0.05 everything else). It is a close call between this and idle, because the scope guard says no evidence means no feature work.

**What would change it:**
- Any outside report, bug or adopter attempt: reorder to that evidence immediately (it outranks this whole note).
- The consumer walk in step 1 finds nothing painful: stop after the guide (a docs-only patch release) and go to the catalog or idle.
- The maintainer wants ScrypathOps quality more than library reach: catalog first. Nothing in the catalog blocks the library, and the reverse is also true.
- Someone names a concrete dependant's pain with testing or soft deletes: promote that item to first and design from their shape.

## 4. Lens notes

**Product and first adopter.** The first thing a real adopter writes after the quick path is a test, and today nothing tells them how to run their Phoenix tests without a Meilisearch container (fact 13 shows the answer exists and is invisible). Highlighting is the next most-asked search-UI feature in the ecosystem but is nobody's first hour. Limits and soft deletes bite in month two, usually as a support question. A real adopter would also ask "what does a failed sync look like in my tests", which the Oban guide gap (fact 14) leaves open.

**API design and architecture.** The public commitments worth fearing are: promoting `Scrypath.Backend` (fact 11; its leaks in fact 17 mean every promise would be partly false), a highlight struct, and a second way to declare "is this searchable" beside `search_records/2`. The allowlist keys are the cheapest pattern: they already carry `rankingScoreThreshold` and friends, have a validation function, and the Plane B guide gives them a documented home. Lesson from other ecosystems: Haystack's abstraction layer became an obstacle (`done-enough-assessment.md`); Searchkick's `should_index?` and Scout's `shouldBeSearchable` both turned into the source of "why is my record missing" questions, so a predicate must ship with a status-visible reason, which is more design than it looks.

**Security.** Highlighting is the only item with a real footgun: `_formatted` values contain the pre and post tags inside field text, and the vendor page does not say the field text is HTML-escaped (U). A Phoenix developer will `raw/1` it. Any highlight feature must ship with an escape-then-wrap recipe and a test with a hostile title. The testing guide must not suggest disabling the Meilisearch API key checks or logging keys. The limits item is a mild availability matter (unbounded paging cost), nothing more.

**DevOps and CI.** All candidates sit in the root library and run in existing lanes (`core`, `package`, `repository-contracts`, `backend`). Docs changes are guarded by `docs_contract_test.exs` and `docs --warnings-as-errors`; a new guide means an ExDoc group entry (the Phase 193 regroup has drift guards, so a new file must be added to `mix.exs` groups or the guard fails, which is the cheap consistency check to run first). Highlight needs one live Meilisearch assertion in the `backend` lane and a `Req.Test` unit test for payload shape. No new dependency anywhere; the testing guide's snippets need `plug` in the adopter's test env, which any Phoenix app has.

**DX and accessibility.** Highlight markup is an accessibility matter on the adopter's side (`<mark>` is announced differently from `<em>`); the guide should show `<mark>` rather than the vendor default. Testing guide snippets should be copy-paste and compile-checked by a docs test, not prose.

**Maintainer cost.** The milestone as sketched is about 12-15 plans and five new public promises for zero known users. The narrow version is about 5-7 plans, one new public promise (six allowlist keys), and the first plan is docs only and can ship as a patch release. Every item added also adds a contract test, a guide row, a docs-truth guard, and release notes, which this repo has made expensive on purpose. The maintainer's rule "value to the point of diminishing returns" applies: the first two items are the last ones where the guess is cheap.

## 6. Adversarial pass against my own recommendation

- **"You are inventing work."** Partly true. Fact 4 says silence lane is the default, and facts 1 to 3 say no adopter has asked for anything on this list. Answer: the recommendation is explicit that this is trigger three (a deliberate strategic product decision by the maintainer), and step 1's guide fixes a false claim (fact 6) and documents an existing option (fact 13), which is docs truth, not feature breadth. Steps 2 and 3 are the part the scope guard would not approve on evidence alone, so they are conditional.
- **"The consumer walk is circular: an agent will find what you told it to look for."** Fair. It is evidence about friction in the docs and in test setup, and it cannot show that anyone wants highlighting. That is why step 2 is gated on the maintainer's call or on a friction finding, and why the walk's output must not be recorded as outside-adopter evidence.
- **"Why not the catalog, which is already queued as CAT-01?"** The catalog serves ScrypathOps, which is not on Hex (`ROLLING-ROADMAP.md`), so it also serves zero known users, costs more (new dependency tree and a NIF per the roadmap), and does not touch the Core Value. It remains a legitimate maintainer choice; if the maintainer prefers it, the guide in step 1 can still ship as a plain docs PR beforehand.
- **"A guide that says 'stub with Req.Test' ties you to Req."** True: `req_options` and the Meilisearch client are tied to Req already, and `meilisearch_client` (a module override) is a second path. The guide commits to documenting the existing option, which is cheaper to retract than a new module, but retraction would still break anyone who copied it. Mitigation: state the promise level in the guide ("supported while the transport is Req").
- **"Highlight via `per_query` allowlist is not as reversible as you claim: adopters will depend on `_formatted` key names."** Those are the vendor's names, so the dependence is on Meilisearch, not Scrypath. The reversible claim holds for the Elixir option names; I rate it reversible with medium confidence because there is no usage to break.
- **"Deferring the predicate leaves a soft-delete footgun in inline mode."** True, and the documented workaround is two lines. If a single real report arrives, it moves to first; the grilling questions are already listed in section 3.
- **"You deferred `Scrypath.Testing`, but the maintainer's own tests needed three fakes."** The maintainer owns the seam; an adopter owning an HTTP stub is the more common Elixir convention (Req.Test, Bypass-style), and a public fake would need the seam leaks fixed first (fact 17). If the guide shows the HTTP stub is too heavy for realistic tests (inline sync polls tasks, so a stub needs several routes), that is the evidence that flips this to a small `Scrypath.Testing` with a recording backend. The walk in step 1 is where that shows up.
- **"Escaping of `_formatted` is unverified."** Yes (fact 10). Resolve it with one live Meilisearch query against a title containing `<script>` before writing any highlight docs. Until then assume unescaped.

**Evidence that would flip the recommendation:** an outside issue or discussion thread (reorder to it); a second dependant appearing in Hex's reverse-dependency list; the consumer walk finding more than about three friction points in the first hour (then widen step 1 into docs truth only, still without new API); the guide's Req.Test snippet failing to cover inline sync in under about 25 lines (then `Scrypath.Testing` gets an ADR); the maintainer preferring the catalog or idle.
